## 2. G1 코드·안전 게이트
### 2.1 S-1: SHADOW가 운영 DB를 열지 않는다 (해결)
이전 설계는 `mode=ro`로 운영 DB를 읽어서 SQLite의 SHM 상호작용을 배제하지 못했다. 새 설계는 운영 DB를 **아예 열지 않는다**.
| 구성요소 | 내용 |
|---|---|
| 별도 상태 | `shadow.state_dir`(필수)에 SHADOW 전용 DB, 커서, 잠금, 실행 폴더, 스냅샷. SHADOW는 쓰기 가능한 **자기** DB를 쓰고 운영 DB·lease는 건드리지 않음 |
| 경로 가드 | 빈 값·상대 경로·드라이브 루트·UNC 거부. 섀도 경로 안의 reparse point(junction, symlink) 거부. 포함/중첩/동일 거부(대소문자 무시). 운영 폴더 및 그 상위 폴더와 파일 정체성(볼륨+파일 인덱스) 비교로 별칭 차단. 폴더 생성 후 한 번 더 검사. 판단 불능이면 시작하지 않음 |
| 객체 수준 방어 | GitHub 전송 객체가 읽기 전용(쓰기 호출은 예외), 러너는 리뷰를 시작할 수 없음(ShadowRunner), 승인·디스패치 꺼짐, `Config.state_dir`(운영 폴더를 만들고 반환하는 속성)는 SHADOW에서 한 번도 읽히지 않음 |
| 명령 일관성 | status·recover·reconcile·watch 모두 모드에 맞는 DB와 잠금 경로를 사용 |
증거 (SYNTHETIC + REAL_API_READ_ONLY):
- Windows 파일 핸들 tripwire: 운영 DB 역할의 표지 파일을 **공유 거부로 열어 둔 채** SHADOW 전체 사이클과 실제 `watch` 명령을 실행했다. 그 파일을 여는 시도가 있었다면 공유 위반으로 즉시 중단됐을 것이다. 중단되지 않았다. 표지 파일 바이트·폴더 목록 불변, 잠금·실행·스냅샷은 SHADOW 폴더에만 생성.
- 실제 PRIVATE 저장소에 대한 `watch` 3사이클: HTTP는 GET 7회뿐, 디스패치 0, 감사 기록(WATCH_START, SCAN_START×3, WATCH_END)은 SHADOW DB에만 있음.
- `Config.state_dir` 접근 즉시 실패 시험, 운영 폴더가 존재하지 않아도 동작·생성하지 않음, 겹치는 경로는 아무것도 만들기 전에 중단, 두 SHADOW 감시기는 동시에 못 뜨지만 LIVE 잠금과는 독립.
- 한계: 실제 호스트 프로세스의 파일 I/O 추적(예: Process Monitor)은 NOT_RUN. 위 증거는 실행한 코드 경로에 대한 것이다.
- 참고: 이전에 관측한 SHM 변경은 이 설계에서는 발생할 수 없다(운영 DB를 열지 않음).

### 2.2 S-2: 신뢰 루트 앵커 독립성 (구현 완료, 이 호스트는 거부됨)
문제 인식: 신뢰 루트와 핀을 같은 계정이 바꿀 수 있으면 핀은 보안 경계가 아니다.
| 항목 | 내용 |
|---|---|
| 새 검사 | LIVE에서 감시기가 실행되는 **자기 계정**(사용자와 소속 그룹)의 유효 권한을 Windows API로 계산해, 신뢰 루트 파일, 그 폴더, 핀을 담은 설정 파일, 그 폴더에 쓰기 계열 권한이 하나라도 있으면 `TRUST_ROOT_NOT_INDEPENDENT`로 거부(기본 enforce). 항목 없음·권한 읽기 실패도 통과가 아니라 거부. 보고에는 역할만 기록하고 경로는 기록하지 않음 |
| **이 호스트의 실측** | 실제 Windows API 시험에서 현재 사용자는 자기 프로필의 파일을 수정할 수 있고 로컬 관리자 그룹 소속이다. 따라서 **현재 구성(대화형 관리자 계정이 감시기를 실행, 파일이 그 프로필에 있음)에서는 LIVE 승인이 `BLOCKED_TRUST`** 이다 |
| 통과하는 구성 | 신뢰 루트·설정을 관리자만 쓸 수 있는 폴더에 두고, 감시기는 **비관리자 계정**으로 실행하며, 승인자 개인키는 **다른 기기**에 둔다. 이 구성은 아직 만들지 않았다(호스트 변경, 승인 필요) |
| 권한 분리 매트릭스 | 승인자 기기: 개인키만. 호스트 관리자: 신뢰 루트·핀·설정(쓰기). 감시기 계정: 읽기만, 쓰기 불가(검사로 강제). 저장소 쓰기 권한자: 커밋 가능, 승인 불가 |
| 버전 래칫·폐기·회전·동결 | v0.2.4에서 구현·시험, 이번에 재확인 |
| 시계 | 제공자 Date 헤더와 5분 비교(기존) + **제공자 시간 고수위 표시**: 제공자 시계가 5분 넘게 거꾸로 가면 거부(신규). 로컬 시계를 되돌려 만료된 승인을 되살리는 시나리오도 거부(시험) |
| 승인자 서명 도구 (신규) | `tools/approval_signer.py`: keygen, sign, check. sign은 REQUEST·READY·패키지의 저장된 바이트에서 모든 서명 필드를 계산하고 불일치·잘못된 커밋·168시간 초과 유효기간을 거부, 승인을 덮어쓰지 않으며 개인키를 출력·복사하지 않음. check는 감시기와 같은 검증을 커밋 전에 오프라인으로 실행. 도구 산출물이 전체 감시기 파이프라인에서 리뷰를 **정확히 1회** 디스패치함을 실서명으로 시험 |
| 미실행 | 운영 승인키·신뢰 루트의 실제 생성·배치, 비관리자 실행 계정, 실제 ACL 구성 (모두 승인 필요) |

### 2.4 이번에 찾아 고친 결함
1. **문서와 코드 불일치**: 후보 패키지에 들어가는 `docs/CUTOVER_RUNBOOK.md`가 폐기된 SHADOW 설계(mode=ro, 형제 폴더)를 설명하고 있었다. 새 설계에 맞게 고치고, 런북이 실제 코드의 식별자를 언급하고 낡은 문구를 포함하지 않는지, 제목의 버전이 패키지 버전과 같은지 검사하는 시험을 추가했다. v0.2.7이 이 때문에 폐기됐다.
2. **간헐적 시험 실패**: 시험용 ZIP 생성 헬퍼가 현재 시각을 항목에 기록하고 ZIP 시각 해상도는 2초라서, 같은 내용을 두 번 만드는 사이 2초 경계를 넘으면 바이트가 달라져 `test_B5…`가 무작위로 실패했다. 제품 결함은 아니다. 2초 경계에 맞춘 재현으로 원인을 확정하고 고정 시각으로 수정한 뒤, 문제 시험을 200회·전체를 10회 반복해 0 실패를 확인했다. v0.2.6이 이 때문에 폐기됐다.
3. **임시 사본 잔존**: 이전 세션에서 SHADOW 리허설이 중간에 중단되어 임시 폴더에 운영 DB 사본이 남아 있었다. 제 임시 폴더임을 확인하고 삭제했다.
4. **이메일 형태 합성 값**: 반출 검사 오탐을 없애기 위해 시험의 합성 값에서 이메일 형태를 제거했고, 시험 고정 데이터에서 소유자 핸들을 제거했다.
