## 3. 이번 변경과 이유
1. **결함 수정 `StateStore.try_claim` (state_store.py, orchestrator.py)**: 실제 CLI 진입점 E2E 에서 `scan` 프로세스 2개를 동시에 실행하면 같은 승인 요청에 대해 reviewer 가 2회 시작됨을 재현했다(수정 전 `model_calls=2`). 원인: 중복 판정이 "읽기(VALIDATED) 후 무조건 UPDATE CLAIMED" 라서 비원자적이었고, `watch` 만 단일 실행 잠금을 가진다. 수정: `UPDATE ... WHERE state IN (미발송 상태)` 단일 문장 compare-and-set, 패배한 프로세스는 `IN_PROGRESS_SKIPPED` 후 발송 0. SHADOW(읽기 전용) 저장소는 claim 하지 않음.
2. **격리 진입점 E2E 신규 (tests/test_cli_entrypoint_e2e.py, e2e_launcher.py, e2e_claude_stub.py)**: 별도 프로세스로 실제 `cli.main` 실행. 실제: Config 로딩, 신뢰 루트 pin·ACL·버전, **실제 Ed25519 서명 검증**, GitHubTransport, orchestrator, RealReviewRunner(argv·stdin·JSON 파싱), SQLite 상태, 결과·영수증 게시. 대체: 네트워크(루프백 합성 GitHub 서버), `claude` 실행 파일(호출 횟수만 세는 stub). 라벨 `HOST_ISOLATED`(운영 LIVE E2E 아님).
3. **단위 시험 tests/test_try_claim.py 15개**.
4. 버전 0.2.14, 런북 첫 줄.

## 5. 독립 리뷰어에게 요청하는 구체 점검
(a) `try_claim` 이 모든 발송 경로에서 유일한 관문인가(`_retry_publish_only`, 재개 상태, 논리 키가 다른 정책 revision 의 중복), 죽은 프로세스가 남긴 CLAIMED/REVIEW_RUNNING 처리(`seal_interrupted` 는 exclusive 일 때만). (b) E2E 가 놓치는 경합(`scan` 과 `watch` 동시, 서로 다른 정책 revision). (c) GitHub 전송: 핀 commit 읽기, add-only 업로드, 게시 실패 후 재시도의 중복 위험. (d) 신뢰 루트 `trust_root_independence=warn` 단일 사용자 운영의 위험 표현이 적절한가. (e) Windows 호환(`claude.cmd` 실행, 인코딩). (f) 토큰 파일 형식: 감시기는 `github.token_file` 을 **원문 토큰 텍스트**로 읽는다.
