## 3. B — C 단계 ETW 재측정
### 실 GitHub 읽기 (C_REAL_GITHUB_READ = PASS)
- 최소 권한 fine-grained 토큰(해당 저장소 한정, Contents 쓰기 거부 확인)을 시험 계정에 시험 한정 임시 사본으로 전달(접근 제한, 종료 후 덮어쓰기+삭제 확인). 토큰 값은 어떤 출력·로그·게시물에도 없다.
- 3주기, 1회 약 6초. GET 7회: 저장소 조회 3, 커밋 조회 3, 트리 조회 1. 상태코드 200×5, 304×2. 쓰기 메서드 0, 신규 REQUEST/READY 0, 모델 0, Telegram 0, `no dispatch` True. 이 시험은 Dropbox LIVE와 동시에 존재했고 단일 LIVE는 유지되었다.
- 1차와 2차 실행의 읽기 결과(호출 수, 상태코드, 감사 이벤트)는 같았다. 저장소 트리 해시는 실행 사이에 달라졌다(원격에 새 커밋이 있었음).

### ETW 계측 (FAIL_UNTRUSTED_MEASUREMENT)
- 1차(22:22): 이벤트 70,669건 중 대상 PID 0, 양성 대조 0. (이 실행의 스크립트 기록에는 추적 파일 삭제가 완전하지 않았다고 되어 있다.)
- 2차(22:37, 수정 스크립트): 이벤트 54,580건, 서로 다른 PID 129개. 시험 프로세스의 **자체 출력 PID와 실행 PID가 14524로 일치**하는데 ETW에서 14524의 이벤트는 **0건**. 미끼 파일(독립 통제된 안전한 읽기 시도) 열기는 PID **25308**에서 1건, 샌드박스 SHADOW 폴더 이벤트는 PID 25308(104건)과 다른 4개 PID(6988, 17468, 25128, 25380)에서 관측.
- 판정: 인계서 §4-3에 따라 양성 대조가 지정 PID에서 검출되지 않으므로 `ETW=FAIL_UNTRUSTED_MEASUREMENT`. PID 상관관계가 틀렸으므로 "시험 프로세스가 운영 `state.sqlite3`/`-wal`/`-shm`/`watch.lock`에 접근하지 않았다"는 결론은 **이번 실행으로 입증되지 않았다**. 운영 이벤트 분류 수치(시험 PID 기준 0건)는 PID가 어긋나 있어 증거로 쓰지 않는다.
- 참고 수치: 다른 PID(실행 중인 Dropbox 감시기)에서는 해당 4개 항목 이름이 있는 이벤트가 14건 관측되어 추적 자체가 그 항목명을 볼 수 있음은 확인되었다. 그러나 이것이 시험 프로세스의 무접근 증거는 아니다.
- 원인은 확정하지 못했다. 가설: (a) ETW CSV의 PID 열이 프로세스 생성/호스팅 구조 때문에 `os.getpid()`와 다른 값을 보인다. (b) 인터프리터 구성(런처/자식)이 PID 귀속을 바꾼다. (c) 시험 계정으로의 실행 방식(보조 로그온) 때문에 귀속이 달라진다. 추적 원본 파일 6개는 **관리자만 접근 가능한 샌드박스에 보존**했고 게시하지 않았다.
- 다음 시도 제안(미실행, 승인 범위 밖 아님): Kernel-Process 공급자를 함께 켜 프로세스 트리(부모/자식)를 확보하고, 스레드 ID(TID)로 미끼 열기를 시험 프로세스의 메인 스레드와 교차 검증한 뒤 PID 열 귀속을 판정한다. 이 보강은 사용자의 관리자 셸 실행이 한 번 더 필요하다.
- 정리: 시험 계정 비활성 복구, 토큰 임시 사본 삭제 확인(두 실행 모두). 운영 상태 폴더 항목 이름 전후 동일. 크기·수정시각 비교는 실행 중인 운영 감시기가 자기 DB를 쓰므로 증거로 삼지 않았다.
