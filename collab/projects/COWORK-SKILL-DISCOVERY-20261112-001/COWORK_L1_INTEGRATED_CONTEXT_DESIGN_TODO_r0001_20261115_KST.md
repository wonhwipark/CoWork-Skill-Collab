## 1. 목표와 완료 범위

새 창에서 공통 진입점 하나를 읽으면 다음 네 가지를 연결해서 파악할 수 있도록 설계한다.

1. **협업 운용:** 요구·스킬 개발 → 분리된 독립 리뷰 → GPT 판정 → 승인된 전달 → 적용 결과.
2. **L1 업무·지식:** 기존 Work 선택 → 필요한 분석/변환 → Work/Evidence → 지식 후보·보완 → 승인 게시/readback → 원래 Work 연결·후속 재사용.
3. **두 흐름의 연결:** 승인된 스킬·계약을 업무에서 사용하고, 그 결과로 드러난 문서 정정·스킬 결함·지식 보완을 각각 맞는 Work와 정본으로 되돌린다.
4. **지속 갱신:** 현재 상태는 해당 CURRENT에서 조회하고, 구조·역할·경로 또는 스킬 계약이 바뀔 때만 지도·카탈로그를 변경한다.

아키텍처 그림의 연결선은 책임·전달 관계다. 자동 호출·설치·리뷰·지식 게시가 구현되거나 실행됐다는 뜻으로 사용하지 않는다.

## 4. 탑뷰 설계에 반드시 들어갈 두 층과 연결

| 층/접점 | 포함할 흐름 | 정본·경계 |
|---|---|---|
| 협업 운용층 | 요구/변경 → 개발·시험 → 독립 리뷰 → 판정 → 승인된 전달/적용 확인 | CoWork PRIVATE의 Work/결과/리뷰/영수증. Windows Claude가 회사 L1 소스를 직접 분석하는 것으로 그리지 않음 |
| 업무·지식층 | Work 검색/재개 → 기존 분석/변환 → Work/Evidence → 후보/Preview·보완 → 승인 게시 → readback·Work 연결 → 후속 재사용 | 업무용 Workspace/팀 Knowledge 역할. GitHub.com의 동명 저장소로 위치 추정 금지 |
| 사용 연결 | 승인된 패키지·정확한 스킬 계약/허용 인계 → 업무 실행 | 설치 확인, Job 활성화, 분석 성공, 결과 조회, 지식 게시를 각각 구분 |
| 피드백 연결 | 허용된 비민감 결과·변경 요구 → 분류·판정 → 적절한 Work 보완 → 정본 갱신·원격 확인 | 원본 코드/로그/상세 MSC/고객자료/비밀을 PRIVATE로 옮기지 않음. 자동 전송·MCP API가 존재한다고 가정하지 않음 |
| 지속 맥락 | 공통 지도 → 관련 CURRENT·근거 → 필요한 스킬 → 결과/피드백 기록 → 다음 창 재개 | 지도에는 일반 진행·최신 버전·리뷰 상태를 복사하지 않음 |

통합도는 공통 지도에서 한눈에 보이게 하고, 같은 전체 그림을 여러 현행 문서에서 별도 관리하지 않는다. 상세 개정본은 책임·인계·정책·검증 경계를 설명하고 공통 지도와 필요한 계약을 연결한다.

## 5. 피드백·업데이트 설계의 분기

| 피드백 유형 | 기본 처리 | 남길 정본·결과 |
|---|---|---|
| 설명/링크 오류 | 사실·경로 확인 → 문서 정정 | 문서 소유 Work의 결과/CURRENT. 구조·경로가 바뀐 경우에만 지도 수정 |
| 스킬 책임·계약·기능 결함 | 기존 계약과 비교 → 영향 범위/기존 Work 확인 → 필요한 개발·시험/리뷰 | 해당 스킬 CoWork Work. 계약 변경이면 카탈로그·연결 설계의 영향 부분 갱신 |
| 분석 근거 부족/불일치 | 원래 업무 Work에서 부족한 항목만 보완 | Kernel이 허용하는 Work/Evidence. 입력 revision·근거·검증 상태 보존 |
| 지식 내용·분류·적용성 보완 | 기존 후보/정본 비교 → Preview/필요 근거/유효 승인 → 게시/readback·Work 연결 | 업무 Knowledge의 게시 revision + 원래 Work 결과. 링크 실패는 링크만 복구 |
| 운영·권한·비용 범위 변경 | 현행 상태·기존 승인 범위를 확인하고 변경 범위만 별도 판단 | 해당 운영 Work의 CURRENT/근거. 문서 게시·피드백 수용을 운영 승인으로 해석하지 않음 |

모든 요청에 새 Work를 강제하지 않는다. 같은 목적·원래 작업은 재개하고, 다른 책임·범위의 실제 작업만 기존 등록 계약에 따라 구분한다. 지식 재사용 결과에서 새로운 스킬 결함이 드러나면 기존 CoWork 작업과 참조로 연결하되 업무 원본은 업무 환경에 보존한다.
