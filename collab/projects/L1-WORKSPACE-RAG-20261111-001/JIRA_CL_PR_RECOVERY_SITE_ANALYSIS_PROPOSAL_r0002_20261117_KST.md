# Jira·CL·Merged PR 기반 복구 지점 분석 — CNF 미수신 timeout 제외 비교평가

- 작성: 2026-11-17 KST / r0002
- 기존 Work: L1-WORKSPACE-RAG-20261111-001

- 피드백 판정: 수용. 기존 구현 사실은 사용자 제공 정보로 반영하며 GPT 직접 코드 검증과 구분
- 범위: 나머지 오류의 분석·복구 방안 비교와 저사양 모델 운영 제안

## 1. 결론

현재 입력과 제약에서는 과거 Jira·CL·PR 근거로 사건 순서를 복원하고, 정상 상태·자원 관계가 처음 깨지는 지점을 확인한 뒤, 그 상태·자원을 소유한 기존 실패 처리·정리·재설정 경로에 연결하는 방안을 권장해요.

추천 구성은 다음과 같아요.

- 분석: 이력과 실제 코드의 상태·자원 조건을 함께 검증
- 검출: 해당 오류를 정상 동작과 구분할 수 있는 가장 이른 확정 지점
- 수행: 영향을 받는 상태·자원을 실제 소유한 기존 처리 경계
- 검증: 대상 오류와 그 주변 정상 경로를 재현하고 복구 후 조건을 확인
- 저사양 모델: 이슈·시나리오 하나씩 순차 분석하고 고정 근거·미확인을 저장

모든 비-timeout 이슈에 복구 코드를 넣는 목표는 적합하지 않아요. 예방, 국소 복구, 상위 복구, 원인 수정 필요를 판별하는 과정까지 포함해야 안전해요.

## 2. 명확한 제외 범위

| 범위 | 판정 |
|---|---|
| REQ 전송 후 대응 CNF를 받지 못해 timeout에 진입하는 이슈 | 제외 |
| 해당 timeout 검출·재시도·pending 정리·기존 recovery 구현 보강 | 이번 요청에서 제외 |
| 이미 그 recovery에서 처리하는 늦은 CNF·중복 정리 | 새 후보로 다시 등록하지 않음 |
| CNF는 도착했으나 실패 status·내용 오류를 잘못 처리하는 이슈 | 독립된 실패 메커니즘과 기존 커버 범위 확인 후 포함 |
| timeout과 독립적인 release/config 경쟁·잘못된 상태 전이·부분 적용 | 포함 후보 |

분류는 이슈 제목의 timeout 키워드가 아니라 실제 실패 메커니즘을 기준으로 해요. 기존 구현으로 해결된 동일 이슈를 상태 경쟁 등의 이름으로 다시 발굴하지 않아요. 기존 recovery와 상태·자원을 공유하는 신규 후보는 소유 범위와 중복 진입 방지만 대조하며, 이를 timeout recovery 재설계 과제로 확장하지 않아요.

## 3. 분석 방안 비교

아래 평가는 실측 속도·정확도·결함 감소율이 아닌, 사용자가 제시한 입력과 제약을 기준으로 한 GPT의 정성적 설계평가예요.

| 분석 방안 | 효과가 좋은 부분 | 안정성·오판 위험 | 저사양 모델 부담 | 제안 |
|---|---|---|---|---|
| CL/PR diff 중심 역추론 | 수정 의도·직접 영향 함수를 빠르게 찾음 | 수정된 줄을 원인 또는 복구 위치로 오인. 주변 상태·자원·다른 revision을 놓칠 수 있음 | 작음 | 탐색 시작점으로 사용 |
| 로그·증상 중심 추적 | 실제 사건 순서와 최초 관측 이상 확인 | 로그 누락·코어별 순서 차이·관측 지점과 원인 지점 차이. 기존 timeout 사례로 편중될 수 있음 | 로그 범위에 따라 변동 | 로그가 있을 때 교차 근거로 사용 |
| 전체 코드의 상태·오류 조건 일괄 탐색 | 알려진 이력 밖의 누락 분기 발견 가능 | 정상적인 중간 상태를 오류로 오인. 후보 폭증·근거 부족·반복 문맥 손실 | 큼 | 초기 기본 경로로는 보류 |
| 과거 이슈 + 좁힌 코드 경로 + 상태·자원 조건 대조 | 실제 발생 근거와 코드 의미를 함께 확인. 복구 소유 경계까지 추적 | revision·전이의 정상성·정리 권한·복구 후 조건이 검증돼야 함 | 이슈/절차별 분할로 관리 가능 | 권장 기본 방식 |

권장 방식은 다른 세 방식의 필요한 근거를 목적에 맞게 결합하는 구성이에요. 이력 수집, 코드 분석, 로그 분석을 별도 전용 엔진으로 재구현할 필요는 없어요.

## 4. 복구 삽입 방식 비교

| 삽입 방식 | 장점 | 주요 위험 | 적용 판단 |
|---|---|---|---|
| 오류를 발견한 곳마다 flag 초기화·return 추가 | 변경이 작아 보이고 증상 확산을 빨리 차단 가능 | 상위 절차 대기, 자원 누수, SW/HW 불일치, 필요한 종료 통지 누락, 이중 정리 | 계약이 단순한 부작용 전 입력 거부 등 제한된 경우 |
| 기존 소유자의 실패 처리·rollback/release/reconfigure 경로 재사용 | 복구 범위·순서·권한·기존 종료 처리를 유지하기 쉬움 | 정상 release와 오류 복구의 전제 차이를 확인해야 함 | 이번 업무의 우선안 |
| 새로운 공통 복구 엔진·정기 상태 감시 | 여러 오류를 한곳에서 관리할 수 있음 | 정상 중간 상태 오탐, 동시성·수명·타이밍 복잡도와 실행 부담 증가 | 기존 경로의 반복적 gap이 입증될 때 재검토 |
| 광범위한 모듈·RF/PHY reset | 국소 복구로 일치를 보장할 수 없는 범위 대응 가능 | 다른 Stack/CC 영향, 서비스 손실, 중복 reset, 반복 발생 은폐 | 국소 복구 불가 시 기존 상위 조정 경로로 이관 |

기존 함수라는 이유만으로 안전하다고 간주하지 않아요. 현재 task/IRQ 문맥, lock, 자원 소유, 부분 진행 상태, 호출 순서, 정상 종료 통지, 재진입 허용 여부가 이번 오류와 맞아야 재사용할 수 있어요.

## 5. 남은 오류를 어떻게 분류하고 대응할까

이 표는 실제 발견 결과가 아닌 분석 대상 분류예요. 우선순위는 실제 Jira의 영향·반복성·증거·재현성으로 정해요.

| 오류 유형 | 확인할 근거 | 기본 처리 방향 |
|---|---|---|
| 상태·이벤트 순서 오류 | 허용 상태/이벤트 조합, 정상 중간 상태, 해당 시점의 소유 절차 | 부작용 전이면 기존 규칙으로 거부·지연·무해 처리. 상태가 훼손됐으면 소유자 경로에서 정리 |
| 수신한 오류 응답·반환값 처리 누락 | 실패 값이 전달되는 경로와 호출자의 후속 상태 변경 | 상태를 더 진행시키기 전에 오류를 전파하고 실제 획득 자원 정리 |
| 설정·자원 획득의 부분 성공 | 어느 단계까지 실제 성공했는지, 역연산·취소의 지원 여부 | 안전하게 되돌릴 수 있는 범위만 rollback. 불가역 HW 적용은 소유자 재설정/상위 이관 |
| release/config·중복 이벤트·재진입 경쟁 | 같은 객체·세대·자원에 대한 동시 접근, 수명과 종료 소유자 | 기존 직렬화·요청 식별·종료 처리 재사용. 하나의 종료·정리만 성립하도록 검증 |
| SW 상태와 HW/PHY 상태 불일치 | 유효한 완료 정보·readback·기존 재동기화 절차, 관측 정보의 신뢰도 | 추가 의존 동작을 제어하고 검증 가능한 상태로 재동기화. SW flag 단독 초기화 금지 |
| Stack/domain/CC 간 자원 소유 불일치 | 공유 자원의 현재 소유자·예약·공식 우선순위와 허용 절차 | 해당 공유 자원 조정자가 복구. 다른 모듈이 전역 상태를 임의 수정하지 않음 |
| 잘못된 값·범위·고정 자원 부족 | API 전제·배열/bitmask/인덱스 범위·자원 획득 결과 | 부작용 전 검증과 실패 통지 우선. 불필요한 reset을 추가하지 않음 |
| 값은 유효하지만 계산·선택이 틀린 논리 결함 | 요구·입력·계산·선택 규칙과 기존 수정 | 정상/오류를 런타임에 구분할 수 없다면 원인 수정·관측 보강 필요 |
| 메모리 손상·복귀 기준 불명 | 상태/자원 자체의 신뢰도·기존 치명 오류 정책 | 신뢰할 수 없는 상태를 국소 복구했다고 보고하지 않고 기존 상위 오류 처리로 이관 |

assert에 걸렸다는 사실만으로 복구 가능하다고 판단하지 않아요. 반대로 오류를 발견했어도 입력을 정상적으로 거부하고 상태를 보존할 수 있다면 별도 reset이 필요하지 않을 수 있어요.

## 6. 권장 분석 절차

1. Jira·CL·PR와 기존 Work를 묶고 각 변경의 역할을 구분해요. Fix·integration·backout·재적용·참고 변경을 섞지 않아요.
2. 사용자 제외 범위와 기존 recovery 적용 범위를 먼저 표시해요. 같은 메커니즘은 제외하고 독립 오류만 계속해요.
3. 문제 빌드, 기존 수정 전후, 이번 삽입 대상의 실제 revision·빌드 옵션을 고정해요.
4. 수정 함수·직접 호출부·비동기 수신자부터 정상 상태·자원 소유 관계를 확인해요. 필요한 공유 자원 경계만 추가 조사해요.
5. 정상과 실패 시나리오에서 최초 불일치를 찾아요. 변경 diff만으로 원인을 확정하지 않아요.
6. 관측 가능한 검출 조건과 실제 복구를 수행할 소유자 경계를 따로 적어요.
7. 기존 실패 처리 경로 재사용 가능성을 확인하고 예방/국소 복구/상위 이관/원인 수정 필요로 판정해요.
8. 후보의 파일·함수·anchor, 진입 조건, 실제 정리 자원, 복귀 상태, 정상 종료 통지, 재진입, 실패 시 이관을 정리해요.
9. 대상 오류와 주변 정상 시나리오를 재현하고 자원·상태·다음 정상 동작을 확인해요.
10. 결과는 기존 Work의 허용 artifact/Evidence로 보존해요. 새로운 Kernel 스키마·원장·미확인 API는 만들지 않아요.

대표 이슈 한 건에서 이 순서를 완주하고, 다음 이슈는 같은 분류의 복제 사례보다 다른 실패 유형을 순차 선택하는 것이 효율적이에요. 한 이슈가 여러 독립 실패 시나리오를 가지면 산출물은 구분하되 기존 Work를 불필요하게 분할하지 않아요.

## 7. 정상 상태를 정의할 때 주의할 점

단일 flag의 값만으로 오류를 판단하면 정상적인 과도 상태를 잘못 복구할 수 있어요. 해당 상태 조건은 절차·전이 단계·소유자·현재 유효 작업 범위 안에서 정의해요.

가상 조건 예시는 다음과 같아요.

- 자원 사용 권한이 필요한 동작 직전에 해당 Stack/domain/CC가 유효한 권한을 갖는지
- 작업 종료가 확정된 뒤 그 작업이 소유했던 예약·참조가 남아 있지 않은지
- 설정 적용 완료를 SW에 반영할 때 대응되는 실제 성공 근거가 있는지
- 객체 수명이 종료된 뒤 그 객체의 이전 이벤트가 새 작업 상태를 바꾸지 않는지

위 조건은 실제 코드의 변수·함수·지원 기능을 뜻하지 않아요. 정상 중간 상태, 실제 관측 가능성, 기존 직렬화·메모리 가시성, 변경 권한을 대상 코드로 확인해야 해요. cross-core 상태를 검증할 수 있는 근거가 없으면 단순 읽기 값 비교로 복구를 발동시키지 않아요.

## 8. 구체적인 가상 예시 — 부분 설정 실패

아래는 timeout과 독립적인 분석 형식 예시이며 실제 L1 결함 발견 결과가 아니에요.

1. TX 관련 자원 예약은 성공해요.
2. 다음 HAL 설정이 명시적인 실패 값을 반환해요.
3. 호출부가 실패를 누락하고 SW 상태를 적용 완료로 바꿔요.
4. 다음 정상 이벤트가 잘못된 상태·소유 관계를 전제로 진행해요.

이 경우 후보를 비교해요.

| 후보 | 판단 |
|---|---|
| 다음 이벤트 처리에서 flag만 수정 | 늦은 검출이며 실제 예약·부분 HW 적용을 복구하지 못할 수 있음 |
| HAL 실패 반환 직후 오류를 전파하고 소유자의 기존 실패 정리로 연결 | 우선 검토. 실제 적용 단계·정리 계약·호출 문맥이 맞는지 확인 필요 |
| 전체 RF/PHY reset | 국소 복구의 안전성·재동기화가 불가능할 때 기존 상위 경로로 검토 |

여기서 삽입 지점은 실패를 확정적으로 관측하는 분기이고, 실제 복구 수행은 자원을 소유한 절차의 정리 경계일 수 있어요. 자원 예약 취소만으로 HW 상태가 보장되지 않으면 부분 rollback을 성공으로 보고하지 않아요.

## 9. 복구 후보를 확정하기 위한 필수 조건

아래 조건을 모두 확인할 수 있어야 자동 또는 국소 복구 후보를 권장해요.

- 정상 동작과 구분되는 신뢰할 만한 오류 신호가 있어요.
- 해당 소유자가 필요한 상태·자원을 정리하거나 재설정할 권한을 가져요.
- 복귀시킬 상태가 정의돼 있고 SW/HW·공유 자원의 일치를 확인할 수 있어요.
- 정상 요청의 결과 통지·완료 책임을 보존해요.
- 중복 이벤트·재진입에서도 정리가 중복되거나 다른 작업을 훼손하지 않아요.
- 실시간 지연·실행시간·재시도·공유 자원 영향이 기존 요구 범위 안에 있어요.
- 실패 시 중단·상위 이관 경로가 있으며 성공으로 위장하지 않아요.

조건 일부가 미확인이면 후보와 미확인을 함께 제시해요. 복구 가능성을 높게 보인다는 이유로 상태를 CODE_CONFIRMED나 PASS로 승격하지 않아요.

## 10. 표적 검증 계획

| 검증 | PASS로 판단할 핵심 결과 |
|---|---|
| 정상 및 허용된 중간 상태 | 복구 오탐 없이 기존 동작 유지 |
| 명시적 실패·오류 반환·잘못된 상태 이벤트 | 지정된 검출 조건과 올바른 소유 경로로 진입 |
| 부분 성공 단계별 실패 | 실제 획득·적용된 범위만 안전하게 정리 |
| release/config·독립 이벤트 경쟁 | 일관된 종료 결과·정리 책임 하나가 성립 |
| 반복·중복 이벤트 | 자원 중복 반납·종료 중복 통지·다른 작업 변경 없음 |
| SW/HW 불일치 | 정의된 검증 수단으로 복구 후 일치 또는 상위 이관 확인 |
| 공유 RF/Stack/CC | 허용된 영향 범위 밖의 상태·자원 손상 없음 |
| 복구 중 실패·지속 오류 | 제한된 실행으로 명확한 실패·이관, 반복 reset·무한 루프 없음 |
| 다음 정상 작업 | 복구 직후 flag뿐 아니라 실제 기능이 정상 진행 |
| 실행 비용·조건부 빌드 | 기존 시간·자원 요구와 대상 빌드의 실행 범위를 충족 |

오류 주입은 실제 실패 의미와 부분 수행 상태를 보존하는 지점에서 해야 해요. 일부 부작용을 생략하는 가짜 함수 실패로 잘못된 rollback 안전성을 입증하지 않아요. 실제 HW 적용을 모사하지 못한 시험은 그 한계를 남겨요.

기존 REQ→CNF 미수신 timeout 시나리오를 이번 신규 분석의 검증 대상으로 다시 확장하지 않아요.

## 11. 저사양 모델에 맞춘 운영

| 단계 | 권장 처리 |
|---|---|
| 자료 수집·범위 고정 | 기존 Jira/Mango/Git 도구와 스크립트가 조회·정리. 모델이 변경 이력을 임의 재구성하지 않음 |
| 의미 분석 | 이슈 하나·실패 절차 하나, 변경 함수·필수 직접 연결부부터 분석 |
| 상태 조건 판단 | 전이 전제·소유자·관측 근거·복구 후 조건의 고정 표를 채움 |
| 후보 비교 | 기존 경로 재사용 후보와 대안 2~3개를 근거로 비교 |
| 연속 작업 | revision·코드 anchor·Evidence·미확인을 보존해 다음 단계에 전달 |
| 검증·리뷰 | 모델 추론과 실제 시험 결과를 구분. 복잡한 공유 자원·경쟁은 담당자 검토나 허용된 별도 리뷰로 보완 |

다중 Agent 동시 실행을 전제로 하지 않아요. 저사양 모델의 처리시간·정확도는 이번 회차에 실측하지 않았어요. 문맥 크기만으로 추론 능력이나 안전성을 보장할 수 없어요.

## 12. 기존 스킬 책임과 수정 범위

- p4-code-owner: Jira Fix CL·원본/integration·파일 revision 근거
- l1-github: PR diff와 실제 landing·삽입 대상 적용 상태
- code-analyzer: 상태/자원/오류 전파·호출/이벤트의 코드 사실
- issue-analyzer: 실제 로그가 있을 때 증상·사건 순서 교차 확인
- 기존 Workflow/Kernel: Work·Evidence·판정 연결
- doc-converter: 정상/실패 MSC 표현

이번에는 입력 제외 기준과 기존 분석 artifact의 비교표 내용부터 반영하는 설계를 권장해요. 기존 기능만으로 가능한 시범 분석을 먼저 수행하고, 실제 반복 누락이나 지원 부재가 입증된 부분만 최소 변경해요. 신규 스킬·공통 runtime 감시·RAG·Kernel 필드 추가는 제안의 선행조건이 아니에요.

## 13. 공개 사례 근거와 적용 추론

| 근거 | 확인 내용 | 이번 제안으로의 추론 |
|---|---|---|
| C++ Core Guidelines E.4 | 오류 복구 후 살아 있는 객체는 유효한 상태를 가져야 한다는 원칙 | 정상 상태·자원 관계와 복구 후 조건을 먼저 정의 |
| Linux Devlink Health | 오류 유형별 진단·dump·복구 callback 및 자동 복구 조건 분리 | 오류 검출·근거 보존·복구 수행·반복 억제를 구분. 새 devlink 프레임워크 도입 제안은 아님 |
| Linux mlx5 RX completion 오류 | HW가 보고한 completion 오류를 기록하고 필요 시 관련 queue flush/reset | timeout이 없어도 명확한 오류 신호에 기반해 해당 자원 범위에서 복구하는 실제 예시 |
| Linux PCI Error Recovery | 정지·정리·reset/재설정·resume의 단계적 조정 | 검출 분기와 공유 자원 소유자의 복구 경계를 나눔 |
| EH-Test, ATC 2016 | 드라이버의 실패 함수·오류 처리·자원 사용을 오류 주입으로 시험 | 대상 실패 경로와 자원 사후조건을 표적 검증 |
| Linux Error Injectable Functions | 함수 실패를 강제할 때 반환 계약·부작용 의미를 보존해야 한다는 제약 | 실제 부분 성공 상태를 무시한 오류 주입을 안전성 증거로 사용하지 않음 |

위 사례는 원칙과 구현 예시의 근거예요. 해당 프로젝트의 효과 수치를 모뎀에 일반화하거나 프레임워크·예외·동적 할당 도입의 근거로 사용하지 않아요. 대상 L1의 heap new/delete 금지, 기존 오류 코드·메시지·실행 문맥 정책을 유지해요.

## 14. 현재 판정과 다음 한 행동

- SCOPE_FEEDBACK: ACCEPTED — CNF 미수신 timeout 및 기존 커버 범위 제외
- GPT_COMPARISON: COMPLETED_SCOPE_LIMITED — 현재 입력·제약 기반 정성평가
- RECOMMENDATION: 이슈 근거와 상태·자원 분석을 결합하고 기존 소유자 실패 처리 경로 재사용
- BUSINESS_SOURCE_ANALYSIS / LOW_MODEL_BENCHMARK / RECOVERY_SITE_VALIDATION / CODE_PATCH / RUNTIME_TEST: NOT_RUN
- INDEPENDENT_REVIEW / HOST_INSTALL / JOB / PAID_REVIEW_REQUEST / PUBLIC_DELIVERY: NOT_RUN
- 기존 다른 Work 진행·요청·영수증과 배포 차단 상태는 변경하지 않음

다음 한 행동은 timeout과 독립적이고 원인·수정 근거가 남아 있는 종료 이슈 한 건을 선택해, 정상/실패 시나리오·최초 상태/자원 불일치·기존 실패 경로·후보의 복구 후 조건을 같은 Work에서 읽기 전용으로 대조하는 것이에요. 최초 사례의 실제 결과를 보고 필요한 최소 연결 변경을 결정해요.
