## 1. 핵심 제안

사용자가 제공하는 Jira·CL·Merged PR은 이슈의 의도·변경 이력·증상 단서를 묶는 입력으로 사용하고, 실제 코드의 상태·이벤트·자원 수명 분석을 결합해 복구 위치를 찾는 방식이 적합해요.

권장 역할은 다음과 같아요.

| 역할 | 기존 스킬·도구 | 활용 범위 |
|---|---|---|
| Jira 증상·로그의 시간 순서·정상/비정상 차이 | issue-analyzer | 실제 로그·증상 증거가 있을 때 선택 연결 |
| Jira와 Fix CL의 관계, 변경 파일·integration 원본 | p4-code-owner | P4 이력·수정 근거 수집. 사용자가 말한 p4 issue owner에 대응하는 정본 등록명 |
| PR 설명·리뷰·변경 범위·실제 반영 revision | l1-github | PR base/head와 merged landing 및 대상 브랜치 적용을 구분 |
| 상태 전이·호출/메시지·자원 소유·영향 코드 | code-analyzer | 복구 후보의 코드 사실과 근거를 만드는 핵심 분석 |
| 같은 이슈의 진행·판정·Evidence | 기존 Workflow / Kernel | 기존 Work 재사용. 별도 이슈 원장·신규 스키마를 먼저 만들지 않음 |
| MSC/HTML 표현 | doc-converter | 분석된 사실을 표현. 코드 사실·실행 성공을 판정하지 않음 |

세 스킬만으로도 자료 수집과 1차 가설은 가능하지만, 정확한 복구 위치를 제안하려면 해당 revision의 실제 코드 의미 분석이 필요해요. 이 책임은 이미 존재하는 code-analyzer에 연결하는 편이 맞아요. issue-analyzer를 모든 CL/PR 분석에 강제하면 로그가 없는 입력에서도 불필요한 호출이 늘어날 수 있어요.

여기서 복구는 오류 발생 뒤 상태·자원·진행 중 요청을 정리하고 허용된 정상 절차로 돌아가는 런타임 복구로 해석했어요. 원인 제거 패치, 사전 예방 가드, 진단 로그 추가는 구분해 제안해요.

## 4. 분석은 세 revision을 나란히 비교

종료된 Jira 이슈를 역분석할 때는 아래 세 관점을 함께 두는 것이 좋아요.

| 기준 | 확인할 질문 |
|---|---|
| 문제 발생 빌드의 소스 | 당시 어떤 코드·옵션·상태에서 실패했는가? |
| 기존 수정 전후 | 해당 CL/PR이 원인 제거, 예방, 복구, 진단 중 무엇을 바꿨는가? |
| 이번 복구 코드를 넣을 대상 소스 | 과거 문제가 남아 있는가? 현재도 같은 함수·상태·자원 관계인가? |

변경 이력이 연결돼 있다는 사실만으로 원인을 확정하지 않아요. Jira의 Fix CL 표기·PR 설명·리뷰는 주장과 단서이며, 실제 코드와 시험 증거로 대조해요.

특히 다음을 구분해요.

- PR의 base/head 변경과 대상 브랜치에 실제 반영된 landing 결과
- merge/squash/rebase 방식과 병합 과정의 충돌 해결
- P4 원본 수정 CL과 integration·backout·reapply CL
- 원본 변경이 target 빌드에 포함됐는지와, 이후 되돌림·추가 수정 여부
- 소스 버전과 실제 문제 빌드의 일치 여부
- 파일·조건부 빌드 옵션·제품·RF/PHY 인터페이스 맥락

GitHub 공식 문서에서도 merge_commit_sha는 PR 상태·merge 방식에 따라 의미가 달라져요. rebase된 여러 commit의 전체 효과를 landing 마지막 commit의 parent 한 개와만 비교하면 변경 일부를 놓칠 수 있어요. 실제 반영 범위를 검증해 비교해야 해요.

P4는 파일별 정확한 revision·원본 계보를 확보해요. CL 번호 하나만으로 모든 파일의 revision·제품 소스 트리가 확정됐다고 보지 않아요. Mango에서 과거 파일 내용이 조회되지 않으면 현재 HEAD를 대신 분석하고 과거 사실이라고 보고하지 않아요.

같은 Jira·CL·PR의 명시적 관계와 공식 integration 근거를 우선하고, 설명 키워드가 비슷하다는 이유로 여러 이슈를 자동 합병하지 않아요.

## 5. 권장 분석 순서

1. 같은 목적의 기존 Work를 찾고 Jira·CL·PR 원본 목록과 현재 목표를 확인해요.
2. Jira 본문·댓글의 수집 완전성, CL 역할·계보, PR 설명·리뷰·실제 반영 범위를 모아요. 페이지 누락·접근 실패는 남겨요.
3. 문제 빌드·수정 전후·삽입 대상의 revision과 빌드 맥락을 고정해요.
4. code-analyzer로 변경 함수와 직접 caller/callee부터 상태·메시지·자원 관계를 확인해요. 비동기 이벤트 수신자·공유 자원 때문에 필요한 범위만 확장해요.
5. 실제 로그·덤프가 있으면 issue-analyzer가 동일 빌드·동일 사건의 시간축과 코드 경로를 대조해요. 다중 코어 로그 순서는 timestamp만 믿지 않고 메시지·요청 ID·문맥으로 확인해요.
6. 정상 시나리오와 실패 시나리오를 나란히 놓고 최초 불일치·검출 가능 지점·복구 수행 경계를 구분해요.
7. 복구 후보 2~3개를 근거와 함께 비교하고 주 후보·대안·복구 불가 조건을 제시해요.
8. 기존 오류 처리·release·cancel·상위 reset 경로의 재사용 여부와 부작용을 대조해요.
9. 분석 결과는 기존 Work의 허용된 artifact/Evidence 연결로 보존해요. 신규 Kernel 필드나 Evidence kind를 임의 생성하지 않아요.
10. 후보가 정해진 뒤 허용된 환경에서 표적 오류 주입·회귀시험으로 검증해요.

로그가 없으면 5단계는 생략 가능하지만 실제 발생 순서는 가설로 남아요. 실패 빌드의 실제 소스가 없으면 역사적 코드 경로도 가설로 제한해요. 해당 블로커와 독립적인 이력 정리·현재 코드 후보 분석은 계속할 수 있어요.

## 6. 문제 시점과 삽입 지점을 구분하는 기준

| 구분 | 의미 | 분석 결과 |
|---|---|---|
| 버전상 최초 발생 변경 | 어떤 revision부터 결함이 생겼는가 | good/bad 검증 또는 제한된 이력 가설 |
| 실행 중 최초 이상 | 정상 상태·이벤트 순서에서 처음 벗어나는 순간 | 상태 전이·로그·코드 anchor |
| 오류 검출 지점 | 잘못된 동작과 정상 지연을 구분할 근거가 생기는 순간 | 오류 반환·timeout·상태/순번 불일치 조건 |
| 복구 수행 지점 | 상태·자원·진행 중 작업을 정리할 권한과 실행 문맥이 있는 위치 | 소유 절차의 handler·기존 cancel/release 경로 |
| 복구 완료 지점 | 다시 정상 요청을 받아도 되는 조건이 성립하는 순간 | SW/HW·자원·timer·요청 수명 일치 |

원인 코드와 복구 수행 함수는 다를 수 있어요. 오류를 가장 먼저 발견한 IRQ/타이머 콜백은 복구 요청만 전달하고, 실제 소유 절차가 안전한 task 문맥에서 정리해야 하는 경우도 있어요. 정확한 허용 문맥은 대상 코드와 호스트 계약으로 확인해요.

원인 수정으로 이미 문제가 제거됐으면 추가 복구가 필요한지부터 판단해요. 정상 동작을 손상시키는 광범위한 방어 코드를 자동 추가하지 않아요.

| 진입 조건 | 현재 상태·진행 중 요청·유효한 오류 신호. 정상 지연과 구분되는 이유 |
| 실행 문맥 | task/IRQ/timer, lock 보유, 호출·재진입·비동기 수신 경로 |
| 소유 범위 | Stack·domain·CC·공유 RF/PHY 자원과 다른 절차에 미치는 영향 |
| 정리 내용 | timer·pending·큐·flag·예약 자원·HW 설정과 정리 순서 |
| 동시성 | timeout/CNF 경쟁·release·중복 오류·늦은 응답을 처리하는 방법 |
| 복구 후 조건 | 돌아갈 상태와 SW/HW 동기화 확인, 다음 정상 요청의 허용 조건 |
| 제한 | 최대 시도·시간 예산·복구 중 오류·상위 이관·복구 불가 조건 |
| 검증 | 가설을 반증할 입력, 오류 주입 지점, 관측값과 PASS 조건 |

다음 조건이 입증되지 않으면 추천 후보를 확정하지 않아요.

- 검출 시점에 실제 관측 가능한 조건인지
- 해당 경계가 필요한 상태·자원을 정리할 권한을 갖는지
- 부분 수행된 HW/PHY 동작과 SW 상태를 다시 일치시킬 수 있는지
- 정리나 재시도가 다른 Stack·CC·공유 자원을 훼손하지 않는지
- 복구 실패 시 무한 반복 없이 상위로 이관할 수 있는지

증거수준은 CODE_CONFIRMED / INFERENCE / UNKNOWN으로, 실제 시험은 PASS / FAIL / SKIP / NOT_RUN으로 구분해요. 코드로 위치가 확인됐다는 사실만으로 런타임 복구 시험을 PASS 처리하지 않아요. 정당한 결론은 후보 제안·추가 증거 필요·국소 복구 불가 모두 가능해요.

## 8. L1 Tx 가상 예시

아래는 분석 형식을 설명하는 가상 흐름이며 실제 코드·결함의 발견 결과가 아니에요.

REQ 수신 → TX/RF 자원 예약 → 설정 요청 → 완료 응답 대기 → 정상 응답이면 설정 확정

완료 응답이 누락됐다고 가정하면 다음 후보를 비교해요.

| 후보 | 역할 | 확인할 점 |
|---|---|---|
| 오류 응답·timeout의 검출 분기 | 유효한 진행 중 요청인지 확인하고 소유 절차에 복구 요청 | 단순 정상 지연, 이미 종료된 요청, 늦은 timer 구분 |
| 해당 절차의 cancel/release 담당 경로 | timer·pending·예약 자원·부분 설정을 일관되게 정리 | 기존 함수가 실제 복구에 필요한 범위를 정리하는지, 현재 문맥에서 호출 가능한지 |
| 상위 RF/PHY 복구 조정 경로 | 국소 정리로 SW/HW 일치를 보장할 수 없을 때 이관 | 다른 Stack/CC 영향과 중복 reset·재진입 방지 |

단순히 timeout에서 pending flag만 해제하면 이전 CNF가 뒤늦게 도착해 다음 요청을 완료 처리하는 문제가 남을 수 있어요. 기존 요청 ID·generation·현재 상태 검사를 재사용할 수 있는지 확인하고, 없다면 그 부재를 입증한 뒤 최소 보완을 검토해요.

Dual SIM·ULCA·ENDC는 해당 이슈가 공유 자원에 관여할 때만 범위에 넣어요. 모든 모듈을 매번 확장 조사하지 않아요. 구현 단계에서는 heap new/delete 금지, 실시간 경로의 지연·blocking 제한, 고정 자원 사용 정책을 유지해요.

## 9. 어떤 방안부터 시작할까

| 방안 | 장점 | 비용·한계 | 판단 |
|---|---|---|---|
| A. 기존 스킬을 순서대로 사용하고 사람이 Evidence를 연결 | 스킬 변경 없이 빠르게 실제 gap 확인 | 일부 인계·결과 정리 수동 | 대표 이슈 1건의 첫 단계 |
| B. 기존 CL/PR Work 흐름에 복구 후보 비교 형식을 연결 | 반복 가능한 분석·근거·판정 | 실제 호스트 API/Evidence 연결 확인 필요 | 기본 운영 목표 |
| C. 후보별 오류 주입·재현 검증 | 위치·정리·재진입 설계의 실제 효과 확인 | 시험 환경·입력 제어·관측 지원 필요 | 삽입 결정 전 필요 |
| D. 여러 종료 이슈의 패턴을 지식화 | 후속 이슈에서 유사 상태·복구 사례 재사용 | 잘못된 과거 결론이 누적될 위험 | 검증 사례가 쌓인 뒤 기존 Updater로 연결 |

추천은 A로 첫 사례를 만들고 B의 필요한 연결만 확정한 뒤 C로 검증하는 흐름이에요. 새로운 전용 스킬·RAG 엔진·별도 원장·다중 Agent 구성부터 시작할 근거는 없어요.

첫 사례에서는 변경 함수와 직접 호출 관계를 시작점으로 좁히고, 로그도 해당 절차의 요청·상태·메시지 범위부터 사용해요. 저사양 LLM이 저장소 전체·전체 로그를 매번 재분석하지 않도록 고정 입력과 기존 산출물을 재사용해요. 처리시간 개선 수치는 실측 전 약속하지 않아요.

## 10. 첫 사례에 필요한 입력과 산출물

| 입력 | 최소 내용 |
|---|---|
| 대표 종료 이슈 | Jira key와 접근 가능한 본문·댓글. 이미 제공된 자료는 재요청하지 않음 |
| 변경 이력 | 관련 CL과 PR URL 목록, 알고 있는 원본·integration·backout 관계 |
| 분석 대상 | 실제 제품·소스 저장소/branch·문제 빌드 revision과 이번 삽입 대상 revision |
| 보강 자료 | 가능하면 실패 로그·덤프·재현 순서·기존 수정 검증 자료 |

번호만 제공돼도 조회를 시작할 수 있지만 실제 소스·빌드 맥락 없이 복구 함수를 확정할 수는 없어요. 접근 가능한 자료에서 먼저 수집하고 남은 필수 정보만 확인해요.

첫 산출물은 다음 네 묶음이면 충분해요.

1. 이슈 조건·변경 이력·대상 revision과 미확인
2. 정상/실패 시나리오와 최초 이상·검출·복구 경계를 표시한 MSC
3. 파일·함수·anchor·진입 조건·정리·복귀 상태가 담긴 후보 비교표
4. 권장 후보·대안·복구 불가 조건과 실제 검증 계획

MSC는 기존 doc-converter 규칙으로 HTML+SVG를 만들고, 각 핵심 step에 코드/로그 근거를 연결하는 방식을 권장해요. 시각화 생성 성공은 시나리오의 사실성이나 복구 효과 검증과 구분해요.

## 11. 후보 검증에서 놓치지 않을 시험

| 시험 | 확인할 결과 |
|---|---|
| 정상 경로 | 복구 오탐·중복 실행 없이 기존 결과 유지 |
| 실패 직전·부분 수행·완료 경계 | 각 시점의 자원·상태가 일관되게 정리 |
| 일시 오류·지속 오류 | 제한 내 복구 또는 명확한 상위 이관 |
| timeout과 정상 응답 경쟁 | 하나의 종료 판정, 상태 오염 없음 |
| 복구 후 늦은 응답·중복 응답 | 종료된 요청이 다음 요청을 바꾸지 않음 |
| 복구 도중 release·재진입 | 유효하지 않은 자원 접근·중복 정리 없음 |
| 복구 중 추가 오류 | 무한 재시도·중복 reset 없이 종료/이관 |
| 공유 자원·다른 Stack/CC | 해당 범위의 상태·동작 손상 없음 |
| 복구 후 다음 정상 요청 | 소프트웨어 flag만 초기화된 가짜 복구가 아님을 확인 |
| 빌드/feature 옵션 차이 | 해당 대상에서 실제 실행되는 코드와 적용 범위 확인 |

이 표는 향후 검증 계획이며 이번 회차 실행 결과는 아니에요. 실제 사례와 무관한 시험을 일괄 추가하기보다 후보의 위험·상태 경계에 해당하는 시험부터 선택해요.

## 12. 기존 설계와 연결할 때의 최소 변경 원칙

- 이력 수집, 정확한 revision, call flow, Work 검색/연결은 기존 기능을 먼저 재사용해요.
- 기존 CLI·Evidence 슬롯·historical snapshot 지원이 확인되지 않으면 해당 항목을 NEED_CHECK로 남겨요. 없는 기능으로 확정하고 재구현하지 않아요.
- 첫 사례는 수동 인계로도 수행할 수 있어요. 자동 파이프라인 전체 완성을 분석의 선행조건으로 만들 필요는 없어요.
- Kernel의 profile/provider/kind/stage나 Work ID 체계를 이번 제안으로 확장하지 않아요. 복구 후보 표는 기존 허용 artifact의 내용으로 시작해요.
- 코드 변경은 분석 결과·수용 범위가 구체화된 다음 해당 code-fix/Workflow의 기존 승인·시험 계약으로 진행해요.
- 검증된 일반화만 원래 Work를 참조해 기존 Updater의 Preview·승인·게시·readback 경로로 연결해요.
- 회사 제한 코드·상세 MSC·로그는 업무 호스트와 허용된 업무 저장소에 보존해요. 이 PRIVATE 보고서에는 공개 방법론·비민감 상태만 포함해요.

## 13. 현재 판정과 다음 한 행동

현재 결과는 분석 방안 제안 완료이며 실제 대상 이슈 분석·복구 위치 확정은 NOT_RUN이에요. 이번 회차에 스킬 수정, Job, 설치, 리뷰 요청, 유료 호출, 운영 전환, PUBLIC 게시를 시작하지 않았어요.

다음 한 행동은 종료된 대표 이슈 1건을 골라, 업무 호스트의 기존 설치본·Jira/Mango/Git 읽기 경로와 revision 조회 가능성을 확인하고 같은 Work에서 읽기 전용 시범 분석을 수행하는 것이에요. 첫 결과를 통해 증거 인계의 실제 gap만 정한 뒤 최소 연결 변경을 판단해요.
