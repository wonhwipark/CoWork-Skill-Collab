## 2. 기존 계약에 대한 판정

- Workflow는 사용자 의도·Work 선택/재개·분석 연결을, Kernel은 Work/Evidence 원장을, Updater는 기술 후보·분류·Coverage·중복/충돌·Preview·승인 연결을 담당하는 방향 유지.
- 기존 Work ID와 Artifact/Evidence 참조로 충분하면 별도 요청 원장·새 필드·새 관리 엔진을 만들지 않음. r0005의 논리 속성을 실제 설치 필드로 가정하지 않음.
- 상세도만으로 개인 지식에 제한하지 않음. 기존 Tier 규칙에 상세 설계·Lifecycle·상세 AS-IS MSC가 그룹 후보로 들어가는지 필요한 조건만 확인.
- 특정 Tier 규칙의 존재만으로 오분류를 확정하지 않음. 기존 판정 순서·입력 조합을 확인한 뒤 실제 정책 충돌만 최소 보완. 개인 후보의 일괄 그룹 전환 금지.
- 기존 대표 MSC 선택 및 NO_MSC_REQUIRED/HOLD 판단을 근거 없이 해제하지 않음. 상세 Scenario 수용 범위와 기존 MSC 재사용 조건을 확인. 정적 흐름과 런타임 순서/타이밍 주장은 분리.
- Updater 후보 상태와 Kernel 허용 stage의 호환성은 계약 점검 대상으로 남김. 임의 stage/field 삽입이나 추정 매핑 금지.
- 게시 성공과 Work 역링크 성공은 각각 관리. 역링크 실패를 이유로 같은 지식을 중복 게시하지 않음. 새 CAS·게시 트랜잭션·복구·별도 영수증 엔진은 확인된 GAP 전까지 보류.
- 그룹 l1sw-dev-knowledge는 검증된 기술 지식 정본, 개인 Workspace/Work Ledger는 업무·Evidence·진행 이력 정본. 동일 기술 사실의 독립 최신 정본을 둘 만들지 않음.
- 원인 검증·수정 반영·시험 성공·현재 적용성은 독립 상태 유지. 원인만 확인된 지식은 수정/시험 미완료를 표시한 별도 게시 후보로만 검토.

r0005의 재사용·G0/G1 구분 원칙은 이미 유효하다. 이번 판정은 r0005 전체를 신규 구현 명세로 채택하는 것이 아니라 실제 기존 기능에 매핑할 최소 범위를 명확히 한다. 원본 r0005와 T01~T24 계획은 보존하고 시험 PASS를 소급하지 않음.

**후속 항목은 현재 기능 누락/결함으로 기록하지 않으며 분류·연계 설계 완료를 막는 조건에서 제외한다.** 단 실제 분석/게시/RAG 완료 판정에서는 검증해야 한다. 기존 접근·소스·owner/root·승인·중복 방지 등 실행 안전 게이트를 해제하거나 E2E PASS를 미리 부여하는 결정이 아님.

분석을 지금 새로 실행하거나 기존 Job을 재실행하라는 지시가 아니다. 운영 호출·모델 사용·게시·설치는 기존 승인 계약을 따른다.

## 4. v0.9 분류표와의 관계

- [분류표 v0.9](../../knowledge/references/L1_NR_LTE_Confluence_Module_Procedure_Feature_Table_v0_9_20261113_KST.md): 사용자 첨부 원문 보존. 검토행 215개(P 120/F 95), 기존 181개 계보 + 신규 확인 후보 34개.

- 이번 피드백은 r0005 연계 설계/기존 기능의 적합성 검토가 중심. 215행 전체 담당자 승인·실제 지원·코드 대응·누락 없음의 검증으로 확대하지 않음.
- v0.9 원문의 B-01(실제 기존 ID/본문 대조 미수행)은 사실로 보존. 시점 해석: “설계 보완 완료”와 “실제 항목 정본 편입 허가”를 분리. 실제 항목 반영에는 기존 ID/기준 본문·근거 확인이 필요하지만 215행 전체 매핑을 현재 설계 검토의 선행 조건으로 만들지 않음.
- v0.9를 등록하는 행위는 지식 정본/metadata 쓰기·215개 일괄 분석·스킬 변경·PUBLIC 배포 승인이 아님.
