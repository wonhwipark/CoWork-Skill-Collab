### M3. 생성 입력의 stale 판정 방법이 없습니다 — 근거가 완비된 틀린 확정이 가능합니다

- **실패 조건**: 생성 헤더가 현재 source revision보다 오래된 상태로 분석에 들어가는 경우. 설계는 생성 입력을 **기록**하라고만 하고, 그 입력이 source revision과 정합한지 **판정하는 방법**을 정하지 않았습니다.
- **근거**: r0005 실행 참조서 §5(77행)의 안전선은 "stale/variant 탐지 **100%**"입니다. Envelope에도 `freshness` 필드가 있습니다(31행). 그런데 stale 판정의 입력이 되는 "생성 헤더가 어느 revision 기준으로 생성되었는가"는 생성 산출물 자체에 없을 수 있고, 설계는 그 확인 경로를 지정하지 않습니다. §1 18행은 설정이 불명확한 TU만 다루고, 설정은 명확하지만 생성물이 오래된 경우는 다루지 않습니다.
- **반례**: 메시지 ID를 정의하는 생성 헤더가 이전 revision 기준이고 현재 revision에서 `MSG_7`의 값이 바뀐 경우. 송신 지점과 등록표를 **그 헤더로** 해석하면 양쪽이 일관되게 맞아떨어져 §2 메시지·payload 규칙을 만족합니다. 송신·수신·payload 근거가 모두 있고 anchor도 유효하므로 "근거 없는 확정 0" 안전선을 통과하지만, 현재 코드에 대한 명제로는 틀렸습니다.
- **최소 보완**: 생성 입력마다 (a) 생성 시점의 입력 revision 또는 생성물 bytes 지문을 획득하고, (b) 그것이 분석 대상 source revision과 어긋나면 해당 TU의 관계를 확정하지 않고 `UNKNOWN`으로 둔다는 규칙을 적습니다. 지문을 얻을 수 없으면 "생성 입력 revision 미확인"을 TU 단위 제약으로 남기고 해당 유형의 확정을 막습니다. G0에 "생성 산출물의 revision 지문 취득 가능 여부"를 항목으로 추가합니다.
- **담당**: 업무 GPT(G0에서 생성 파이프라인의 지문 취득 가능성 확인) → 설계 GPT(규칙 반영).
- **수락 시험**: 일부러 과거 revision의 합성 생성 헤더를 넣고 분석합니다. 메시지 관계가 확정되면 FAIL, `UNKNOWN`과 사유가 남으면 PASS입니다.

### M4. 두 번째 빌드 설정에 접근 못 할 때 합성 반례로 대체하는 경로가 빌드 분기 게이트를 무력화합니다

- **대상 절**: §4.2(58행) "두 번째 업무 설정에 접근할 수 없다면 **합성 반례의 결과와 업무 미검증 범위를 함께 남겨요**", 같은 행의 수락 기준 "필수 반례가 통과해야".
- **실패 조건**: 실제 두 번째 빌드 설정을 못 얻어 합성 반례만 돌린 뒤, "필수 반례 통과"를 충족한 것으로 보고 3단계로 넘어가는 경우.
- **근거**: §2 빌드 분기 행(38행)의 확정 요건은 "해당 TU의 **플래그·생성 헤더·target에서 활성 여부를 확인**"입니다. 이는 실제 빌드 입력에 대한 요구입니다. 합성 반례는 전처리 분기 **해석 로직**은 시험하지만, 실제 업무 빌드의 플래그 전달·생성 헤더·target 구성이 기대대로 해석되는지는 시험하지 못합니다. 58행은 미검증 범위를 "남겨요"라고만 하고, 그 미검증이 게이트 통과를 막는지 여부를 정하지 않았습니다.
- **반례**: 업무 빌드가 플래그를 명령행이 아니라 포함된 설정 헤더로 전달하는 경우. 합성 반례는 명령행 플래그 기준으로 전부 통과하지만 실제 빌드에서는 활성 분기 판정이 전혀 맞지 않습니다. 그래도 2단계 게이트는 통과하고, 3단계의 D1/D3 Map은 빌드 분기 관계가 틀린 상태로 들어갑니다.
- **최소 보완**: 합성 대체 시 **빌드 분기 관계 유형을 2단계 통과 대상에서 제외**하고, 해당 유형은 `업무 미검증`으로 못박아 3단계 Map에서 빼거나 별도 표시합니다. 즉 합성 반례는 로직 회귀용으로만 인정하고 유형 수락 근거로는 쓰지 않는다고 적습니다. 실제 두 번째 설정 확보를 G0 항목으로 승격합니다.
- **담당**: 설계 GPT(게이트 문구) → 업무 GPT(두 번째 실제 빌드 설정 확보 가능성 보고).
- **수락 시험**: 합성 반례만으로 2단계를 돌린 결과에 빌드 분기 확정 관계가 포함되는지 확인합니다. 포함되면 FAIL입니다.

## 3. MINOR

### N1. 계산·별칭으로 만들어지는 메시지 ID가 반례에 없습니다

§2 메시지·payload 행(36행)은 "정규 ID"가 맞아야 한다고 요구하고 반례로 "번호가 같아도 인터페이스가 다른 경우"와 "접미사만 비슷한 REQ/CNF"를 듭니다. 빠진 반례는 **ID가 식으로 만들어지는 경우**입니다. 송신 측은 `MSG_BASE_NR + 7`, 등록 측은 `MSG_UL_SWITCH_REQ`로 적혀 있고 둘이 같은 값인 경우, 토큰 문자열은 다릅니다. 반대로 서로 다른 이름이 같은 값으로 접히는 경우도 있습니다. §1 26행은 "메시지 번호는 검색 키로 활용"한다고만 하고, 정규 ID를 **어떻게 얻는지**(매크로 전개 후 상수 접기까지 수행하는지)는 정하지 않습니다. 제안: 정규 ID의 산출 범위를 "전처리 전개 후의 정수 값"으로 명시하고, 값 산출이 불가능한 ID는 확정하지 않고 후보로 둔다고 적습니다. 시험은 식으로 정의된 ID 쌍을 합성해 둘이 하나의 관계로 묶이는지 확인하는 것입니다.

### N2. 3단계 비교에 쓸 빌드가 두 설정 중 어느 쪽인지 지정되지 않았습니다

§4.2(58행)는 실제 빌드와 분기 반례용 두 번째 설정을 각각 고정하라고 하고, §4.3(59행)은 "같은 소스·빌드·예산·모델 조건에서" 비교하라고 합니다. r0005 실행 참조서 §3.1(54행)은 "다른 build는 별도 stream"이므로 두 설정은 서로 다른 snapshot 계열입니다. 어느 stream의 Map으로 D1/D3를 구성하는지 적혀 있지 않아, 구현자가 두 stream을 합치거나 임의로 고를 수 있습니다. 제안: 비교에 쓸 stream을 하나로 지정하고 다른 설정은 반례 검증 전용으로 한정한다고 한 줄 넣습니다.

### N3. 추출 단계 정답표의 규모가 고정되지 않았습니다

§4.2(58행)는 "P0의 … 정답과 반례를 원문에서 먼저 정하고"라고 하지만 개수를 정하지 않았습니다. r0005 실행 참조서 §5(75행)는 holdout에 대해 "양성 ≥30·음성/반례 ≥10을 사전 고정"으로 규모를 못박습니다. 추출 단계에만 규모 기준이 없어 "필수 반례가 통과"의 강도가 구현자마다 달라집니다. 제안: 관계 유형별 최소 양성·반례 수를 정하거나, 최소한 "유형별 반례 ≥1을 각각 고정하고 그 목록을 사전에 봉인한다"를 적습니다. B2의 하한선과 함께 다루면 한 번에 해소됩니다.

## 4. 요청 항목별 답변

### 4.1 (요청 1) 파일 목록화·TU·모듈 결합이 overload·헤더 내부 linkage·템플릿·빌드 변형을 구분하는가

**네 가지 모두 문서에 명시적으로 등장합니다.** §1 25행이 대체 식별자에 "정규화한 시그니처와 필요한 한정자"(overload), "linkage"와 "헤더의 정적 함수나 익명 namespace처럼 TU에 종속된 심볼은 해당 TU도 구별"(헤더 내부 linkage), "템플릿 특수화"(템플릿)를 넣었고, 빌드 변형은 §1 19행의 "같은 저장소·source revision·build에서만 결과를 결합"과 27행의 빌드 지문으로 다룹니다. 미해소 시 후보로 남기는 규칙(25행)도 있어 **틀린 동일시를 막는 방향은 맞습니다.**

다만 두 가지가 비어 있습니다. 첫째, 이 식별자를 **누가 산출하는지**가 B1처럼 비어 있지 않고 "기존 도구가 제공하는 해석된 심볼 ID를 우선"으로 지정되어 있는데, 그 도구가 실제로 그걸 제공하는지가 미확인입니다(B2). 특히 overload는 **정의 측 식별**과 **호출 측 해석**이 다른 문제입니다. 정규화한 시그니처는 정의를 유일하게 가리키는 데는 충분하지만, 호출 지점이 어느 overload를 부르는지는 인자 타입 해석이 필요하고 이름 기반 도구로는 나오지 않습니다. §2 35행이 "해석된 대상 선언·정의를 대조"로 올바르게 요구하지만, 그 해석의 공급자가 확정되지 않았습니다. 둘째, 템플릿은 "특수화"만 언급되고 **인스턴스화**는 없습니다. 같은 템플릿이 서로 다른 인자로 인스턴스화되어 호출 대상이 달라지는 경우의 처리(하나의 관계인지 별개인지)가 정해지지 않았습니다. 이것은 P0 범위에서 흔하지 않을 수 있어 MINOR로도 올리지 않았지만, 구현 전 한 줄 결정이 필요합니다.

### 4.2 (요청 2) 확정에 필요한 원문 근거와 빠진 반례

§2의 다섯 행은 관계별로 필요한 근거를 구체적으로 적고 있고, 특히 **등록·전달·실행 관측을 각각 별개 명제로 분리한 것**(37행)과 **빌드 조건과 런타임 guard를 분리한 것**(38행)은 이 설계의 강점입니다. 40행의 `Send(MSG_7)` 예시도 네 가지 근거를 각각 요구해 적절합니다.

빠진 반례는 다음 네 건입니다. 각각 위의 항목에서 다뤘습니다.

| 빠진 반례 | 영향 | 항목 |
|---|---|---|
| 같은 키에 등록 지점이 둘 이상(초기화 후 교체) | P0 `registers`가 같은 빌드 안에서 틀림 | M2 |
| 조건이 서로 다른 복수 호출 지점을 한 관계로 묶음 | 빌드 조건 혼합, variant 탐지 실패 | M1 |
| 생성 입력이 현재 revision보다 오래됨 | 근거가 완비된 틀린 메시지 관계 | M3 |
| 식·별칭으로 만들어진 메시지 ID | 같은 관계를 놓치거나 다른 관계를 합침 | N1 |

### 4.3 (요청 3) 증분 갱신이 r0005의 Writer/Reader·snapshot 계약과 맞는가

**대부분 맞습니다.** 설계 53행의 "삭제·이름 변경은 이전 관계와 역참조까지 새 세대에서 철회", "변경 전후 역의존을 함께 봐요", "불변 조각은 bytes와 적용 입력이 검증된 범위에서 재사용", "활성화와 충돌 처리는 r0005 실행 참조서 §3을 적용"은 참조서 §3.5의 "tombstone/역링크 철회, old/new include·매크로·build 역의존 합집합"과 §3.2의 "같은 이름/같은 bytes는 재사용"에 각각 대응합니다. 세대·parent·단일 슬롯 생성 같은 저장 원자성을 설계가 자기 방식으로 다시 정의하지 않고 참조서에 위임한 것도 올바릅니다.

어긋나는 지점은 두 곳입니다. (a) **조회 응답 표현**: 설계 26행의 묶기 규칙이 참조서 §2 Envelope의 레코드 형태(anchor 1개)와 맞지 않습니다(M1). (b) **freshness 판정의 입력**: 참조서는 `freshness` 필드와 "stale/variant 탐지 100%"를 요구하는데, 설계는 생성 입력을 기록하라고만 하고 stale 판정 방법을 정하지 않았습니다(M3). 두 건 모두 저장 계약 자체의 충돌이 아니라 **설계가 채워야 할 빈칸**입니다.

추가로 확인한 정합성: 설계 17행의 "legacy 121개와 분류 합계 120개의 차이를 실제 파일 목록으로 정산"은 r0005 G0-3(인계 32행)과 참조서 §1 root·분모 행(11행)의 요구와 일치합니다. 설계 21행이 "r0005의 질문별 파일·토큰 상한은 소비 하네스에 적용"으로 참조서 §2 보강·fallback(46행)의 상한을 그대로 받는 것도 맞습니다.

### 4.4 (요청 4) G0-1, 대표 모듈 P0 추출 정확도, Qwen 소비 효과 비교와 재현 가능한 수락 기준

**G0-1**: 설계 57행이 "r0005의 첫 행동은 G0-1이에요"로 올바르게 가리킵니다. 다만 설계가 새로 요구하는 G0 항목이 세 개 늘어납니다. 아래 표의 추가 항목을 r0005 G0에 붙일 것을 제안합니다.

| 추가 G0 항목 | 이유 |
|---|---|
| Analyzer가 실제 빌드 기준 해석 심볼 ID를 반환하는가 | B2. 미제공이면 §2 확정 규칙 전체가 적용 불가 |
| 생성 산출물의 revision 지문을 얻을 수 있는가 | M3. 못 얻으면 메시지 관계 확정 금지 |
| 두 번째 실제 빌드 설정에 접근 가능한가 | M4. 불가면 빌드 분기 유형을 유형 수락 대상에서 제외 |

**P0 추출 정확도**: 설계 58행의 기준(잘못된 확정 0, variant 혼합 0, 필수 반례 통과, 동일 입력 재실행과 TU 순서 변경에서 동일 결과)은 **방향이 맞고 재현 가능합니다.** 특히 TU 처리 순서를 바꿔도 같은 결과가 나와야 한다는 조건은 좋은 결정성 시험입니다. 보완이 필요한 것은 하한선(B2)과 정답표 규모(N3)뿐입니다. 재현 가능한 형태로 정리하면 다음과 같습니다.

1. 원문에서 P0 관계 유형별 정답·반례를 봉인합니다. 유형별 반례 ≥1, 봉인 목록의 digest를 먼저 고정합니다.
