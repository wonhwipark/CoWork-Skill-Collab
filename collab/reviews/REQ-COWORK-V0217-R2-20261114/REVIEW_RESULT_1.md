## Non-blocking findings / observations

**N1 — Approval nonce has no replay store (relevant to Q7)**
`skill_collab_watcher/approval.py:417-419` only checks that `nonce` is a string ≥16 chars (`MIN_NONCE_LENGTH`); there is no table or counter anywhere in `state_store.py` that records a nonce as "consumed." Grepped for `nonce`/`used_nonce`/`replay` in `state_store.py`: no matches.
- Failure condition: none today, because replay protection is actually provided by the job-dedup logic (`find_dispatched_logical_job`, F1 fix), which keys on `request_id|request_revision|package_sha256` regardless of nonce. But if the local SQLite state is ever lost or rebuilt (disk replaced, manual `DELETE FROM jobs`, fresh install pointed at an already-reviewed package), the exact same signed `APPROVAL_SIG.json` + `SOURCE_PIN.json` would verify again and trigger a second paid review, because nothing outside the job table remembers that the approval was used.
- Evidence: `approval.py` nonce check (format only), `state_store.py` schema (no nonce table), reliance entirely on `jobs`/`audit_log`.
- Minimal fix: either (a) explicitly document that approval replay protection is bound to local state survival (acceptable for a single-user watcher, but should be stated, not assumed), or (b) add a small `used_approval_nonces` table checked in `_check_approval` alongside the existing dedup.
- How to verify: wipe `state.sqlite3`, replay a previously-processed `REQUEST`/`READY`/`APPROVAL_SIG.json` bundle, confirm whether a second model call happens.
- Not verified: whether this is an accepted operational assumption already documented elsewhere (e.g., CUTOVER_RUNBOOK.md) — I did not read that file in full given budget.

**N2 — `repo_id` is a config-supplied label, not a GitHub-verified identity (Q7, confirms known gap)**
`approval.py:407-408` compares `payload["repo_id"] == trust.repo_id == pin["repo_id"]`, all values that live inside the signed payload and the locally configured trust root JSON — none of them is fetched from GitHub's own repository ID API. Forging a valid approval still requires the Ed25519 private key, so an attacker with only repository *write* access (no key) cannot pass this check by themselves. The actual residual risk is operational: if the same `trust_root.json` (and therefore the same `repo_id` string) is ever pointed at two different repos (e.g., a fork sharing config), a legitimately signed approval for repo A verifies unchanged against repo B. This matches the manifest's stated "known gap" — I confirm it is still true in this version and did not find any additional binding (e.g., to `cfg.github_repo` or a GitHub-side repo ID) introduced in v0.2.15–17.
- Not verified: actual GitHub write-access attack scenarios, since this needs a real GitHub repo/token, out of scope for static Windows-only review.

**N3 — `read_github_token`'s repo-match check is advisory, not authorization (Q7, cli.py:33-55)**
The JSON token-file "different repository" refusal (`cli.py:51-53`) is a courtesy check comparing a `repo` string *written into the token file itself* against `cfg.github_repo`; it does not call GitHub to confirm the token's actual scope. A token file whose `repo` field is simply omitted or lies is accepted (`test_json_without_a_repo_key_is_accepted` in `test_token_file_formats.py` confirms the omitted case is intentional). This is fine for the stated consumer profile (single-user, operator controls their own token file) — flagging only so it's not mistaken for a security boundary.

## Answers to the eight questions

**Q1 (usage-limit wait/resume).** No path found that starts a second paid review for work that already began. `detect_usage_limit` (`review_runner.py:102-116`) classifies as `DURING` (never auto-retried) whenever either billing evidence exists (`total_cost_usd`, `output_tokens`, `cache_creation_input_tokens`) OR the process ran longer than `BEFORE_START_MAX_ELAPSED_SEC` (120s) — the latter is a reasonable belt-and-suspenders in case a refusal is billed as literally $0 but still followed real work. Jobs can't be "lost": a `BEFORE_START` refusal explicitly reverts the job to `VALIDATED` (`orchestrator.py:277-278`) and the global `USAGE_HOLD_COUNTER` prevents even re-downloading the package for any request while held (`orchestrator.py:540-545`), confirmed by `test_while_held_the_package_is_not_downloaded_again`. Waiting is bounded in two ways: `usage_limit_max_wait_sec` caps the hold itself, and `usage_limit_max_deferrals` caps retries before the job becomes a terminal `FAILED` (`orchestrator.py:270-276`) — so it cannot wait forever. The regex `USAGE_LIMIT_RE` / `NON_RETRYABLE_RE` combination is reasonably specific (`you've hit your ... limit`, `usage limit reached`, named limit types) and explicitly excludes admin/spend-cap phrasing via `NON_RETRYABLE_RE`; the one soft spot is that this is pattern-matching on English CLI text, with the comment candidly admitting "no limit was provoked" during testing — the exact production string was never observed. Time-zone/am-pm/date-rollover: `_reset_wait_seconds` parses `am`/`pm` with a 1-12 validity check, handles same-day rollover (`target += timedelta(days=1)` if already passed) and year rollover for month/day forms; this is directly tested (`test_the_cli_time_formats_are_parsed_in_local_time`, `test_a_month_day_that_already_passed_this_year_means_next_year`) and I agree with the test results by re-reading the regex/logic. A normal review whose *output text* happens to mention "weekly limit" as a discussion topic could false-positive match `USAGE_LIMIT_RE` only if it also has zero cost/output tokens and finished within 120s — an edge case but not impossible for a trivial/degenerate review; low severity, not blocking.

**Q2 (StateStore.claim ceilings).** The `BEGIN IMMEDIATE` transaction in `claim()` (`state_store.py:226-265`) makes the ceiling check and the state-flip atomic, closing the race the F3 test (`test_f3_two_requests_cannot_both_pass_a_one_per_day_ceiling`) exercises and that I traced manually. A stale `CLAIMED`/`REVIEW_RUNNING` row cannot block the ceiling forever in the current design because `seal_interrupted(exclusive=...)` runs unconditionally at the top of every `run_scan_cycle` (`orchestrator.py:823`) before any claim is attempted, and it is gated correctly: it only flips rows when the caller holds the exclusive single-instance lock, and `scan`/`watch` always do now (see Q4). It only runs once per `StateStore` instance (`sealed_at_open`), which is correct for `watch`'s long-lived single connection. I did not find a path where `exclusive=False` is passed from `cmd_scan`/`cmd_watch` — both set `rt.exclusive = True` right after acquiring the lock. Not verified: SHADOW-mode or any third caller that might construct `LocalPolicy`/call `run_scan_cycle` with `exclusive=False` outside the lock — the F3 test itself does this (`exclusive=False`) for its second simulated process, which is correct for its purpose (that process never claims the lock) but confirms such a call path exists in test harnesses; I did not find it used in any shipped entry point.

**Q3 (F1 logical-request invariant).** The invariant is: once a `request_id|request_revision|package_sha256` triple has been dispatched (CLAIMED/REVIEW_RUNNING/RESULT_SAVED/UPLOAD_PENDING/terminal) under *any* `local_policy_revision`, no other policy revision's never-dispatched row for the same triple may be claimed. Verified by reading `_process_request_group` (`orchestrator.py:522-529`): the exact-key lookup is tried first; if that row is absent or itself never-dispatched, `find_dispatched_logical_job` searches across all policy revisions but is restricted to `dispatched_states` only (`state_store.py:408-422`), so a never-dispatched row can never "hide" behind another never-dispatched row, and a never-dispatched row cannot be mistaken for a reviewed one. This differs from the old `find_logical_job`, which is still present (`state_store.py:395-406`) but no longer used in this dispatch path (grep confirms `find_logical_job` has no other call site in `orchestrator.py`) — it looks effectively dead code now; worth a note to the author to prune it rather than a flaw. The author's narrowing ("reproduced only with re-signed approval + rollback of policy revision + lost cursor") is appropriately matched by `test_f1_...` in `tests/test_r1_findings.py`, which does exercise exactly that three-part combination (re-sign → re-sign again for original revision with fresh nonce → delete cursors table → rerun) and asserts `runner.calls == 1`. I agree the invariant is now unconditional for the paths I read; I did not independently execute the test suite (no tool access to run pytest in this review), so "PASS" here reflects my own trace of the code, not a reproduced test run.

**Q4 (scan/watch lock + seal_interrupted + exit codes).** `cmd_scan` now acquires `SingleInstanceLock(_work_dir(cfg)/"watch.lock")` before opening the runtime and sets `rt.exclusive = True` (`cli.py:471-492`); `cmd_watch` does the same via a context manager (`cli.py:495-506`). `SingleInstanceLock` (`lock.py`) uses `msvcrt.locking` on byte 0 of a pre-created 1-byte file, held for the life of the open file handle — correctly OS-released on process death/crash without any stale-PID bookkeeping, which is the right approach on Windows and avoids the classic "PID file left behind" bug. A live job's seal is correctly avoided: a second scan/watch can't even get the lock while the first is inside its model call, so it is refused (exit `EXIT_LOCKED`=3, confirmed printed message "already holds") rather than racing to seal it — matches `test_f2_...` and `test_a_second_scan_is_refused_...`. A dead process's job *is* sealed by the next scan, because the OS released the lock and `seal_interrupted` runs at the top of the next exclusive cycle — matches `test_f4_...`. SHADOW refusal: `cmd_watch` explicitly re-raises `ShadowIsolationError` before the generic `except RuntimeError` handler (`cli.py:557-561`), preserving its own exit path; I did not find the equivalent in `cmd_scan` as an explicit except clause, but `cmd_scan` has no surrounding `try/except RuntimeError` at all around `_open_runtime`/`_one_cycle` other than the lock's own `finally` — so a `ShadowIsolationError` raised inside `_open_runtime` would propagate unmodified out of `cmd_scan` to `main()`, which the parametrized test (`test_a_shadow_isolation_refusal_is_not_reported_as_a_lock_failure`, parametrized over `["scan"]` and `["watch", ...]`) confirms both resolve to `EXIT_REFUSED`. I did not read `main()`'s top-level exception mapping to independently confirm exit code 6 beyond what the test asserts (`cli.EXIT_REFUSED`); take the exit-code-6 claim as test-confirmed, not independently traced by me to a literal `6` in source.

**Q5 (publish/receipt failure after a successful model call).** Confirmed the model is never called again. After a successful `review_result`, the job is moved to `RESULT_SAVED` then `UPLOAD_PENDING` (`orchestrator.py:720-721`) and the result is written to local disk (`_save_result_locally`) *before* any upload attempt. If `_publish_result` raises `TransportError`/`UploadConflict`/`AuthRequired`, the job stays `UPLOAD_PENDING` and the handler returns `retry=True` (`orchestrator.py:732-736`); on the next cycle, `_handle_existing_job` detects `RESUMABLE_PUBLISH_STATES` and calls `_retry_publish_only`, which by its own docstring and signature takes no `ReviewRunner` argument ("structurally impossible... to start a claude..."). The operator sees an `UPLOAD_FAILED` audit event with the exception description; the request is not consumed and no extra billing occurs. This resolves cleanly and I found no gap here.

**Q6 (Windows timeout handling).** `review_runner._run` (new in this version) starts the process via `subprocess.Popen` instead of `subprocess.run`, and on `TimeoutExpired` calls `_kill_tree`, which runs `taskkill /F /T /PID <pid>` (kills the whole tree) then also calls `proc.kill()` on the direct child as a backstop, swallowing `OSError` if the process already died — reasonable defense in depth. `test_f5_a_timeout_ends_the_reviewer_process_tree_not_only_its_first_process` uses a real `.cmd` wrapper (`claude.cmd` calling into Python via `%*`) that spawns a grandchild via `subprocess.Popen`, and asserts the grandchild's marker file never appears — this is a meaningful regression test for exactly the `.cmd`-wrapper-plus-children scenario the comment worries about. stdin encoding is explicit `utf-8`/`errors="replace"` on both `Popen(...)` and documented against the Windows ANSI code-page trap (`review_runner.py:304-306`). One gap: `taskkill`'s own failure (e.g., `taskkill` not found, or insufficient privilege against a process owned by a different, perhaps elevated, account) is not checked — `subprocess.run(..., check=False)` silently discards a nonzero return code, and the fallback `proc.kill()` only reaches the direct child, not any surviving grandchildren, if `taskkill` genuinely failed. In the ordinary single-user-watcher profile (same account, no elevation boundary) this is unlikely to matter, but it is not asserted/logged if it does happen — a zombie grandchild could survive silently if `taskkill` fails for an unanticipated reason. Non-blocking given the stated consumer profile, but worth logging `taskkill`'s return code for diagnosability.

**Q7 (trust/identity, replay, crypto-missing).** See N1/N2/N3 above for `repo_id` and token-file findings. Fail-closed on missing `cryptography` is confirmed: `signature_backend.default_backend()` catches the `ImportError` from `Ed25519Backend.__init__` and returns `None` (not an exception, not a silent "verified" default); `approval.verify_approval` explicitly raises `NotConfigured("signature backend is not configured")` when `backend is None`, which `_check_approval` catches and converts into `APPROVAL_UNVERIFIABLE` + `retry=True` — zero model calls, request stays pending, no accept-by-default. This matches the manifest's claim that the "operating interpreter" (no cryptography) never exercises signature verification, and confirms it fails safe rather than silently accepting unsigned approvals. Expiry (`APPROVAL_EXPIRED`/`APPROVAL_NOT_YET_VALID`/`APPROVAL_LIFETIME_TOO_LONG`) is enforced with explicit tz-aware checks and a 5-minute `CLOCK_SKEW` tolerance (`approval.py:37,421-438`) — looks sound on read-through, not independently tested by me beyond reading the code.

**Q8 (combination of changes).** The one gap I can point to concretely is N1 (nonce not a true replay store — the combination relies entirely on local SQLite surviving). The F1/usage-limit/lock interactions I checked explicitly compose correctly: `seal_interrupted` runs before ceiling checks and before usage-limit-hold checks in the same cycle ordering, and the usage-limit hold check (`orchestrator.py:539-545`) sits *before* package download but *after* the F1 dedup lookup, so a request held for usage-limit reasons still can't be double-claimed by a policy-revision rollback in the interim — the state machine ordering looks deliberate. I did not find or construct a scenario combining all of {usage-limit deferral + restart + policy revision + cursor loss + lock} simultaneously myself; I relied on reading the ordering of checks in `_process_request_group`, which is consistent, rather than tracing a concrete reproduction. This is the weakest-verified answer in the set — flagged as unverified below.
