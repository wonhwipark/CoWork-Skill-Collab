# CoWork — 용어·저장소·실행 환경 표기 원칙 V1

- 제정: 2026-11-13 KST
- 적용: GPT 답변, 신규 설계·판정·인계·리뷰 프롬프트, 협업 지침 및 앞으로 갱신하는 문서의 **표현 방식**
- 우선순위: 사용자 최신 요청 → 본 표기 원칙 → 기존 프로젝트별 용어. 기존 기술·보안·승인 계약을 폐기하지 않음.
- 상태: **문서 표현 규칙**. 설치·호스트·권한·게시 정책·LIVE provider 변경 승인이 아님.

## 1. 기본 표현 규칙

- 업무 수행 위치를 두 지역/망 경계로 나누는 기존의 대칭 접두어 표현은 **앞으로 사용하지 않는다**. 사람·도구·저장소·실행 환경을 **실제 이름 또는 기능**으로 지칭한다.
- 저장소 접근 정책, 데이터 반출 허용 여부, 작업 PC와 원격 GitHub의 연결 여부를 **표현 간소화를 이유로 합치지 않는다**.
- 불필요한 위치 수식 없이 **GPT**, **Claude Code**, **업무용 GPT**, **Linux 실행 호스트**, **Windows 작업 PC**, **GitHub PRIVATE**, **GitHub PUBLIC**, **업무용 Git 저장소**, **접근 불가**, **미검증**처럼 역할/권한을 기준으로 쓴다.
- 기존 문서의 파일명·상대 경로·식별자·해시·커밋·영수증·원문 인용은 **변경하지 않는다**. 이전에 작성된 과거 문서와 결과에는 당시 표현이 남을 수 있으며, 이는 **새 지침의 미적용 증거가 아니다**. 새 문서 본문과 새 요청문부터 적용한다.
- 변수·CLI 명령·원본 코드 식별자·API 필드·파일명이 기존 용어를 포함한다면 동작 호환성을 위해 그대로 유지하고, 인접 설명만 새 표현으로 작성한다.

## 2. 정확한 지칭 및 접근 경계

| 실제 대상 | 앞으로 사용할 표현 | 절대 혼동하지 않을 사실 |
|---|---|---|
| `wonhwipark/CoWork-Skill-Collab` | **GitHub PRIVATE 협업 기준 저장소** | 공개 불가/반출 금지 원문까지 게시해도 된다는 뜻이 아님 |
| `wonhwipark/L1Work` | **GitHub PUBLIC 배포·공개 허용 자료 저장소** | 승인된 ZIP 및 비민감 인계·공개 허용 화면만 게시 |
| `l1-workspace` | **업무용 Git의 Work 문서 저장소 (`work_docs`)** | GitHub.com의 동명 저장소로 추정하거나 PRIVATE 협업 저장소와 동일시 금지. 실제 원격·checkout은 작업 PC에서 확인 |
| `l1sw-dev-knowledge` | **팀 공통 지식 저장소** | 개인 Work 기록/지식과 구분, 권한 없는 자동 승격 금지 |
| Windows Claude Code | **Windows Claude Code** 또는 **Windows 작업 PC** | 모델 사용 가능/독립 리뷰 실행은 별도 증거 필요 |
| Linux의 Agent/runner | **Linux 실행 호스트**, **업무용 Agent**, **업무용 GPT** | 실제 설치·MCP/Job/provider 호출은 실측 전 미검증 |
| 개인 Work 지식 | **개인 모듈 지식 / Work 이력** | `works/` 원장과 `module-library/` 설계 후보를 혼동하지 않음 |
| 검토/검증 | **GPT 자체 리뷰 / Claude 독립 리뷰 / 호스트 시험** | 게시·자체시험·독립 리뷰·배포를 서로 다른 상태로 기록 |

## 3. 보안·권한은 그대로 유지

- 회사 코드, 상세 MSC/로그, 고객자료, 토큰·개인키, 승인되지 않은 상세 경로 등 제한 자료는 **GitHub PRIVATE에도 게시 금지**. 반출 허용을 증명할 수 없으면 로컬에 보존하고 결과는 `NOT_POSTED`.
- 역할이 다른 원격 저장소 간 콘텐츠 복제는 데이터 분류·승인·무결성 검증 후 허용한 자료에 한정.
- PUBLIC 게시, 실제 호스트 변경, 유료 리뷰, REQUEST/READY, 신뢰키 생성, 운영 DB·watcher·예약작업, LIVE 전환은 별도 승인. `CURRENT.md`의 최신 실측 상태가 우선.
- GitHub 문서 작성/수정·링크 추가만으로 Windows Claude Code, Agent, Job-list, watcher가 자동 실행되는 것은 아님.
- 문서의 동작 컨셉은 기존 스킬의 구현·실행/접근 권한 증거로 대체하지 않는다. `PASS/FAIL/SKIP/NOT_RUN`, `BLOCKED`를 분리하여 보고한다.

## 4. 새 문서와 인계서 작성 지침

1. 첫 등장 시 정확한 대상 명칭(예: `wonhwipark/L1Work`, `main`, `handoffs/...`)을 제시한다. 이후에는 **PUBLIC 배포 저장소**, **PRIVATE 협업 저장소**, **Linux 실행 호스트** 등으로 간결하게 부른다.
2. 검색 대상과 실행 권한을 명확히 구분한다. `l1-workspace` GitHub MCP 연결이 검증되지 않았으면 **작업 PC의 로컬 Git/스킬을 통한 확인 필요**로 명시한다.
3. 신규 인계 본문·자동생성 지침·사용자 안내에서 구식 위치 접두어를 다시 쓰지 않는다. 기존 파일명/경로에는 자동 변경을 적용하지 않는다.
4. 기존 문서의 비민감 설명을 갱신할 경우 **실제 동작을 바꾸지 않는 용어 수정**만 하고, 감사·해시·정본 인계의 지난 실행 이력을 새 결과로 소급 수정하지 않는다.
5. 변경 기록은 해당 프로젝트 `CURRENT.md`에 필요한 경우만 연결한다. 이 표기 지침 자체는 자동 실행·새 리뷰 요청·LIVE 전환을 발생시키지 않는다.
