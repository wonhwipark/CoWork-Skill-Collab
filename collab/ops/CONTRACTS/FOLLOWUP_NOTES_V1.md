# CoWork — 후속 메모·대화형 노트 처리 지침 V1

- 작성: 2026-11-12 KST / 분류: DOCUMENTATION_WORKFLOW
- 적용: 사용자가 기록·후속 확인을 요청한 CoWork 비민감 메모 및 기존 협업 승인 범위의 프로젝트 노트.
- 목적: 메모를 파일 제공으로 끝내지 않고 PRIVATE 프로젝트 기록과 연결해 다음 상태 확인 때 누락하지 않는다.
- 범위: Markdown 문서 등록·조회·판정·추적. watcher/자동화/새 원장·schema·모델 호출을 추가하지 않는다.
- 상위 경계: START_HERE.md·해당 프로젝트 CURRENT.md·사용자 최신 지시. LIVE 전환·배포·유료 리뷰·사내 변경·PUBLIC 게시 권한을 부여하지 않는다.

## 1. 위치·권위와 공개 경계

1. 기본 정본은 GitHub PRIVATE wonhwipark/CoWork-Skill-Collab, branch main, collab/projects/<project-id>/notes/<memo-name>.md이다. 기존 적절한 노트 위치가 있으면 이동시키지 않고 재사용한다.
2. 프로젝트 CURRENT.md에 메모의 정확한 상대 경로, 제목/목적, 기준 설계/인계 revision, 상태, 확인 조건, 허용된 다음 행동을 연결한다. 메모마다 새 Work/Job/실행 SSOT를 만들지 않는다.
3. Library/대화 첨부는 참고·전달 사본이다. 프로젝트 메모 등록이 요청된 작업에서는 사본만 제공하고 GitHub 정본 기록을 생략하지 않는다. 사용자가 파일 제공만 또는 특정 위치만 요청하면 그 범위를 따른다.
4. 회사 코드·내부 MSC·고객정보·내부 경로/로그·토큰·개인키·반출 미승인 자료는 PRIVATE에도 게시하지 않는다. 원본이 허용되지 않으면 비민감 메모만 남기고 실제 근거는 사내에 보관한다.
5. PUBLIC L1Work는 별도 승인된 전달물만 게시한다. PRIVATE 메모를 자동 복제하거나 기존 PUBLIC 인계서를 자동 개정하지 않는다. 진행 중 작업의 메모는 기존 요청과 구분한다.

## 2. 등록 절차

- 현재 프로젝트 상태와 적용 지침을 먼저 읽고, 사용자가 지정한 실제 메모 원문을 확인한다.
- 같은 목적의 기존 메모가 있으면 경로·기준 revision·내용을 비교해 중복을 피한다. 원문/과거 판단은 보존하고 수정은 개정본 또는 명확한 추가 절로 남긴다.
- 메모가 사용자 설명인지 직접 실측인지 구분한다. 사용자 보고의 수행 요청은 USER_REPORTED_REQUESTED이고 완료·무변경·호출 성공의 증거가 아니다.
- PENDING_RESULT(결과 대기), PENDING_CHECK(자료 확인 대기), DISPOSITION_RECORDED(근거 판정 기록), CLOSED(조건 충족 또는 사용자 종료)를 Markdown 상태 표기로 사용한다. 새 runtime enum/schema 등록 지시가 아니다.
- 상태·조건·다음 한 행동을 CURRENT.md에 기록한다. 단순 게시를 CLOSED나 구현 완료로 승격하지 않는다.
- PRIVATE main에 PR 없이 문서만 게시하고 원격 내용·commit·바이트 hash를 확인한다. 게시/재조회 실패는 NOT_POSTED/UNVERIFIED로 보고한다. 결과 게시 실패 때문에 모델/Job을 다시 실행하지 않는다.

## 3. 다음 상태 확인 때 함께 읽을 자료

프로젝트 CURRENT.md를 먼저 읽은 뒤 현재 범위와 관련된 다음 자료를 함께 확인한다.

- CURRENT.md가 연결한 열린 notes/*.md와 미해결 follow-up.
- 해당 프로젝트 및 관련 리뷰의 *_FOR_GPT_*, INTERACTIVE_ADDENDUM_*와 사용자 질의·관찰/가독성/구조 노트.
- 메모가 참조하는 실제 결과·영수증·승인 상태. 사용자 보고, G0 설치 사실, G1 설계 가정, 자체 시험, 독립 리뷰를 구분한다.

새 자료가 없으면 결과 대기를 유지한다. 자료를 받으면 메모 항목별로 근거·수용/수정 수용/거절/보류/추가 확인·다음 행동을 기록하고 기존 계약과 충돌하는지 판정한다. 같은 전체 리뷰를 근거 없이 반복하지 않는다. CLOSED는 근거가 있는 항목에만 적용한다.

## 4. 진행 중 요청과 실행 경계

- 후속 메모는 진행 중 인계서나 기존 실행을 자동으로 대체·취소·재실행하지 않는다.
- 결과를 먼저 확인하고 빠진 연결·문구·기존 스킬 재사용의 실제 gap만 후속 보완한다. 미확인 API/record를 새 구현 항목으로 확정하지 않는다.
- 기존 Knowledge/metadata·Work/Evidence·Kernel registry/schema·운영 DB/Job/예약 작업에는 메모 등록으로 쓰지 않는다. 사내 조사 범위는 해당 인계서와 별도 사용자 지시를 따른다.
- '내일 결과를 보고 확인' 같은 후속 조건은 문서의 대기 조건이다. 자동 예약·백그라운드 감시·watcher 요청·알림·모델 호출을 생성했다는 뜻이 아니다. 실제 예약/자동화 요청은 별도 실행 수단과 승인 경계로 처리한다.
- 이 문서 절차는 기존 provider/LIVE 상태를 변경하지 않고 Dropbox 복제·운영 watcher 변경을 요구하지 않는다.

## 5. 긴 사내 결과를 줄이는 방식

사내 상세 원문을 외부에 옮기도록 요구하지 않는다. 기존 결과에서 허용된 범주형 요약을 만들고 상세 근거는 사내에 둔다. 반출 승인·내용 적합성이 없으면 외부 전달은 보류한다.

요약은 후속 판단 자료이며 사내 설치본·실 API/통합 검증의 대체 증거가 아니다. 문서 확인/연결 설계/실제 호출을 구분하며 미확인을 '없음'이나 PASS로 바꾸지 않는다. 메모 원문에 이미 간단한 형식이 있으면 재사용한다.
